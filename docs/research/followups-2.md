# OpenMinis iOS SessionFileV2 sync (workspace-file sync over CloudKit): SessionFileChangeTracker + ChatStoreSyncHydrators SessionFile section + ICloudSharedZoneTransport asset paths

## Key findings
- DELETES on the wire are real CloudKit record deletions, not tombstone records: outbound markDirty(op='delete') -> SyncCore batchDeletes (SyncCore.swift:386-392) -> transport queues CKSyncEngine .deleteRecord(recordID) (ICloudSharedZoneTransport.swift:989-1010); inbound arrives via zoneChanges.deletions parsed back to SyncRecordID (ICloudSharedZoneTransport.swift:1451-1459). No absent-asset record, no soft tombstone for files.
- CRITICAL GAP: inbound SessionFileV2 deletions are NEVER applied on the receiving device. ChatStoreSyncHydrators.registerAll registers SessionFileV2 with builder+merger only, NO deletionApplier (ChatStoreSyncHydrators.swift:42-46); SyncCoreHydrators.applyRemoteDeletion falls through to a documented no-op 'default-keep' (SyncCoreHydrators.swift:84-94). A file deleted on device A stays on device B's disk forever.
- RENAMES have no first-class representation: iSH fakefs emits op=1 (delete) for the old path and an upsert for the new path (SessionFileChangeTracker.swift:76, comment at 209-218 says unlink/rename surface guest-shape paths). On the wire that is CK-delete(old composite key) + new record(new key) — and because inbound deletes are no-ops, a rename leaves a stale copy under the old name on peers.
- CONFLICT POLICY is whole-file LWW by file mtime, two layers: (1) declared .lastWriteWinsByServerEtag in SyncedTypes.swift:213 — on CKError.serverRecordChanged the transport surfaces .conflict(id, serverRecord) and re-queues our record merged onto the server's etag/system fields (ICloudSharedZoneTransport.swift:1562-1581); SyncCore feeds the server record through processInbound and does NOT clear dirty, so our version re-pushes next batch (SyncCore.swift:553-558). (2) mergeSessionFile apply-side guard: skip if local file mtime is newer than remote updatedAt by >5s slack ('local newer' skip, ChatStoreSyncHydrators.swift:384-398); otherwise removeItem+copyItem whole-file overwrite. No field-level or content merge — concurrent edits on two devices resolve to whichever file has the later mtime; the loser's content is destroyed.
- DEBOUNCE/COALESCING: fs events coalesce in-actor per (sessionId, relPath) LWW (SessionFileChangeTracker.pending dict); SyncCore.scheduleSend debounces 3s (defaultSendDelay, SyncCore.swift:155-156) and cancels prior pending task; during agent streaming sends are deferred (syncSendDeferred, ChatStore.swift:3591-3599) with dirty rows still persisted; at agent-turn end flushPendingSyncDirty runs scanAndMarkSessionFiles per touched session then one scheduleSend (ChatStore.swift:3609-3626). Tracker drain happens inside sendNow just before loadDirtyRecords (SyncCore.swift:355-360, drainSessionFileChangesIntoDirty at 816-857). drainAllWithMtimeFilter suppresses open-without-write false positives: upsert drains only if host mtime >= lastTouchedAt-1s; otherwise kept pending, dropped after 30s decay (SessionFileChangeTracker.swift:131-190). CK push batches capped at 20 records (nextRecordZoneChangeBatch, ICloudSharedZoneTransport.swift:1357). Inbound poll fetchRecentV2 every 120s querying updatedAt > cutoff (24h window / last-run anchor minus 5min slack), plus CKSyncEngine token-driven pushes.
- SIZE LIMITS & EXCLUSIONS: per-file cap UploadPolicy.maxFileSizeBytes, default 1 MB, UserDefaults 'cloudSync.v2.upload.maxFileSize' (UploadPolicy.swift:88-98); enforced at scan time (ChatStore.swift:3676-3678) and again at build time (ChatStoreSyncHydrators.swift:328-333, oversize -> builder returns nil, dirty row dropped). Synced buckets: ALL FOUR of workspace, attachments, browser, offloads (tracker whitelist SessionFileChangeTracker.swift:265; scan list ChatStore.swift:3649) — yes, offloads/ and browser/ ARE synced. Excluded: memory/skills/shared/mounts (own sync mechanisms). Junk-dir skip list only on the scan path (NOT the fakefs tracker path): __pycache__, .git, .svn, .hg, node_modules, .tox, .venv, venv, .build, .eggs, .mypy_cache, .pytest_cache, .ruff_cache, __pypackages__, .gradle, .idea, plus hidden files (ChatStore.swift:3630-3636, 3661). Whole category can be toggled off via UploadPolicy category 'sessionFiles'.
- NO CONTENT HASHING for SessionFileV2 — nothing dedupes unchanged files. scanAndMarkSessionFiles marks EVERY file under the four buckets dirty on every agent-turn flush regardless of change (ChatStore.swift:3683), and buildSessionFile always re-reads and re-attaches the asset; the CKAsset re-uploads. SHA256 echo-hash tricks exist only for ProviderConfig/EnvVar (CloudSyncEngine.lastUploadedProviderConfigHash) and MemoryGlobal uses a content-equality string compare before write (ChatStoreSyncHydrators.swift:938-948). SessionFile relies purely on echo-suppression maps.
- ECHO-LOOP AVOIDANCE: two 30s-TTL 'recently pushed' maps — SyncCore.recentlyPushedIds stamped pre-send (SyncCore.swift:446-467) filters inbound in processInbound (SyncCore.swift:641-645); transport-level recentlyPushedRecordNames stamped at CK save-ack (ICloudSharedZoneTransport.swift:1519-1538) filters CKSyncEngine's own-write re-delivery (1403-1414). mergeSessionFile does NOT backdate the applied file's mtime — unlike MemoryGlobal/SOUL/MCP which do fm.setAttributes([.modificationDate: remoteUpdatedAt]) after apply (ChatStoreSyncHydrators.swift:963-966). On iOS this is survivable because the fakefs tracker only sees iSH-kernel writes, not host-side FileManager.copyItem; the residual echo (scanAndMarkSessionFiles re-marking applied files) is absorbed by the TTL maps + remote LWW skip.
- RESURRECTION GUARD: mergeSessionFile refuses to recreate files of a recently-deleted session unless the remote record is newer than the deletion (ChatStore.isResurrectionOfDeleted, ChatStoreSyncHydrators.swift:371-380); session deletion also drains the tracker for that session so explicit op=delete wins over stale upserts (drainSession, SessionFileChangeTracker.swift:195-197, called from FileBrowserView.swift:1144).
- EVENT LIFECYCLE (full chain): fakefs_record_change (deps/ish/fs/fake.c C ring buffer) -> ISHKernel handler on serial queue, sid resolved from fs_context via MinisFsRouter with fallback to ISHExecutionCoordinator.mountedSessionIdSnapshot captured at event-receive time (SessionFileChangeTracker.swift:280-325) -> actor recordBatch coalesce -> SyncCore.sendNow drain (mtime filter) -> markDirty sync_dirty_records -> buildSessionFile (stat, mime via SessionFileMimeMap, PortableAsset) -> CKRecord+CKAsset save via CKSyncEngine, batch 20 -> peer receives via token stream or 120s CKQuery poll -> echo filter -> mergeSessionFile (resurrection guard, local-newer LWW, mkdir -p, removeItem+copyItem). Outcomes: success clears dirty; conflict re-merges server + re-push; transient keeps dirty; NOT_FOUND re-queues one fresh etag-less create (ICloudSharedZoneTransport.swift:1590-1619).

## Data formats
- CKRecord type 'SessionFileV2' in CloudKit private DB, container 'iCloud.com.openminis.app', zone 'minis-shared'. recordName = 'SessionFileV2:<sessionId>:<subdir>/<relativePath>' (composite key 'sessionId:relativePath'; may contain '/', CJK, emoji — validated only against control chars, <=255 chars, no leading '_', no trailing ':' by isValidCKRecordName, ICloudSharedZoneTransport.swift:264). Fields: sessionId(String), relativePath(String), fileSize(Int), mimeType(String?), updatedAt(Date = sender's file mtime), plus 'asset'(CKAsset with file bytes), 'asset_size'(Int), 'asset_mime'(String), 'syncSchemaVersion'(Int), 'syncMinimumCompatibleVersion'(Int?). Schema declared in SyncedTypes.swift:187-217 (conflictPolicy: .lastWriteWinsByServerEtag, version 1, scope .perParent(SessionV2))
- SQLite dirty queue: sync_dirty_records(record_type, record_id, zone_name, operation 'upsert'|'delete', priority INTEGER, created_at REAL). SessionFile rows written as v1 type 'SessionFile' and mapped to 'SessionFileV2' via ChatStore.v2RecordType(forV1:) (ChatStore.swift:4326-4338); loadDirtyRecords(v2Only:true) filters by whitelist v2SyncRecordTypes (ChatStore.swift:4730-4753), LIMIT ~395/batch
- On-disk layout: host <Library>/MinisChat/minis/<sessionId>/{workspace,attachments,browser,offloads}/... ; iSH guest bind-mount /var/minis/<subdir>/... — both path shapes resolved to '<subdir>/<rel>' by SessionFileChangeTracker.resolveSessionRelative (SessionFileChangeTracker.swift:224-268)
- In-memory change event: (sid, rawPath, op Int [1=delete, else upsert], tsNs Int64) from fakefs_record_change in deps/ish/fs/fake.c, coalesced to [sessionId: [relPath: Change(op, lastTouchedAt)]] (last-write-wins per relPath)
- Transport persistence: <Library>/MinisChat/cloud-sync-v2/state-v2.bin (JSON-encoded CKSyncEngine.State.Serialization) and etag-cache.plist (NSKeyedArchiver'd CKRecord system fields, cap 5000 entries)
- PortableRecord/PortableAsset intermediate: fields dict + assets dict {key: (fileURL, size, mimeType)}; inline-vs-asset threshold 750KB for string fields (assetInlineThreshold, ICloudSharedZoneTransport.swift:80), but SessionFile content always ships as CKAsset regardless of size

## Reusable for desktop
- Composite record identity 'sessionId:relativePath' with per-file whole-record replace + attached blob — maps cleanly to a LAN sync message {sessionId, relPath, size, mime, mtime, bytes}
- Producer/consumer actor pattern: fs watcher -> in-memory per-path LWW coalescing dict -> atomic drain-at-push-time, with the mtime-catch-up filter (drain only if mtime >= observedAt-1s, keep pending else, 30s no-op decay) to suppress open-without-write false positives — directly reusable over a real FS watcher (chokidar/ReadDirectoryChangesW)
- Debounce architecture: 3s coalesced send, defer-during-agent-turn with crash-safe dirty persistence, full-directory rescan safety net at turn end, junk-dir exclusion list and per-file size cap as user policy
- Apply-side guards worth inheriting verbatim: local-newer LWW skip with clock-drift slack, recently-deleted-session resurrection guard, and dual echo-suppression maps (pre-send stamp + ack-time stamp, TTL ~30s)
- DELIBERATE DIVERGENCES DeskMinis MUST make: (1) mtime-backdate applied files to the record's updatedAt (the MemoryGlobal/SOUL pattern at ChatStoreSyncHydrators.swift:966) — on desktop the real FS watcher WILL see the sync engine's own writes (unlike iOS fakefs which only sees iSH writes), so without backdating + a self-write suppression set, apply->watch->re-push is a guaranteed infinite loop; (2) implement the missing inbound file-deletion applier (unlink on peer) since iOS's no-op default-keep leaves stale files; (3) add first-class rename (or at least delete-applies) so renames don't duplicate files; (4) add content hashing (per-file SHA256) to skip unchanged-file re-uploads — iOS re-pushes everything each turn; (5) decide concurrent-edit policy consciously: iOS is whole-file mtime LWW with silent loser destruction — for two live desktops a conflict-copy (file.conflicted-<device>.ext) or at minimum a version vector is safer than inheriting silent LWW
- Conflict plumbing shape: transport surfaces .conflict(id, serverRecord) -> core applies server copy locally via the normal merge path, keeps the dirty row, transport re-queues local version on fresh etag — a clean generic retry loop that translates to any transport with compare-and-swap semantics

## Open questions
- Exact fakefs op-code enumeration beyond 1=delete (deps/ish/fs/fake.c fakefs_record_change was not read) — whether rename emits a distinct op or literally unlink+create pair, and whether truncate/chmod emit events
- Applied-file mtime after copyItem: the CKAsset staging file's mtime (download time) is what the dest inherits — could be newer OR older than remote updatedAt, subtly affecting later LWW comparisons; iOS never resolved this because they skip backdating for SessionFile
- Whether the every-turn full rescan (scanAndMarkSessionFiles marking all files dirty) causes measurable re-upload bandwidth in practice, or whether CKSyncEngine dedupes identical asset bytes server-side (no evidence of client-side dedupe found)
- The fakefs tracker path applies no junk-dir filter — a shell 'npm install' inside workspace/ would enqueue every node_modules file individually (each under 1MB cap) as SessionFileV2 records; unclear if anything else guards this
