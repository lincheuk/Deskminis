### 1. 出站客户端的对端身份验证（防错连/中间人）——一审命门 1 重写

**结论：PASETO 握手层防错连 + sync.hello 挑战应答双向互认 + jti/aud/短 TTL 防重放，三层叠加。**

**一审指出的错误已修正**：原「RPC 响应能被 authKey 解密验证」错误——[`rpc/server.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/rpc/server.ts) L91-92 响应是明文 `ws.send(JSON.stringify({...result}))`，不经 authKey 加密。PASETO v4.local 只在握手 URL `?paseto=<token>` 鉴权，握手后的 RPC 流量是明文 JSON-RPC。因此出站拨号仅靠 PASETO 握手**无法双向证明对端身份**（任何能解 PASETO 的服务端都是配对设备，但客户端无法确认服务端就是预期那台——除非服务端也拿出 authKey 证明）。补出站互认协议如下：

**层 1 · PASETO 握手层（防错连投毒）**：
- 出站 PASETO payload 增 `jti`（随机 UUID v4）+ `aud`（对端指纹，12 hex）+ 短 TTL 60s（出站专用，替代 10min 会话 TTL——出站场景拨号即用即弃，不需要长票据）
- 服务端 `additionalVerify`（[`remote/index.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/remote/index.ts) L96-108）解 PASETO 后增校验：`payload.aud === myFingerprint`（防投递到错对端）+ `payload.exp > now`（60s 窗口）+ **jti 重放缓存**（服务端维护 `Set<string>` 已见 jti，60s 过期清理；同一 jti 重放 → 401 拒绝）
- 拨错地址的服务端没有 PairingKey，PASETO 解不开 → 401（握手层拦截错连投毒）

**层 2 · sync.hello 挑战应答（双向互认）**：
- 连接建立后、**任何同步流量前**，OutboundClient 发 `sync.hello` RPC（authMode=remote，新增方法）：`{ nonce: <16 字节随机 hex> }`
- 服务端收到 `sync.hello`，从 `conn.peerFingerprint`（命门 2 新增字段，additionalVerify 填充）找到对应 PairingKey，算 `mac = HMAC-SHA256(authKey, 'm3c-hello' || nonce)`，返回 `{ mac, listenPort }`（listenPort 用于端口漂移自愈，必改 4）
- OutboundClient 用本地持有的 authKey 算同样 HMAC，比对返回的 mac：
  - **不匹配** → `ws.terminate()` + 退避重连（伪造 hello / 中间人无 authKey 无法算正确 mac）
  - **匹配** → `onOnline(peerFp)` + 开始同步流量
- `sync.hello` 必须在 `sync.push`/`sync.pull`/`sync.dirty` 之前完成——OutboundClient 在 `onOnline` 前不处理任何同步逻辑

**层 3 · 威胁模型（写明防住了什么）**：
| 威胁 | 防护层 | 说明 |
|---|---|---|
| 错连投毒（拨到恶意/错误地址） | 层 1 PASETO | 错地址服务端无 PairingKey，PASETO 解不开 → 401，连接不建立 |
| 数据泄露（RPC 响应被截获） | 层 2 sync.hello + LAN 直连 | RPC 响应是明文（rpc/server.ts L91-92），但只有通过 sync.hello 互认的连接才会发同步流量；截获者无 authKey 无法伪造 hello mac，无法注入恶意连接获取数据；LAN 直连无公网暴露面 |
| token 重放（PASETO 被截获重放） | 层 1 jti + 60s TTL | jti 已见缓存拒重放；60s 短 TTL 窗口极小；aud 校验防跨设备重放 |
| 中间人（MITM 篡改同步流量） | 层 2 sync.hello + M3a 配对码带外交换 + 指纹人工比对 | MITM 无 authKey 无法算正确 hello mac；配对码 8 字 5min 过期带外交换（[`pairing.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/remote/pairing.ts) L64-65）+ 指纹人工比对（M3a §2.1）已防配对期 MITM；出站地址是配对时习得的真地址（决策 2） |

**不引入额外挑战应答冗余论证**：sync.hello 是必要的——PASETO 握手只证明「客户端是配对设备」（客户端向服务端证明），但出站场景需要双向证明（服务端也要向客户端证明它持有 authKey）。sync.hello 的 HMAC 挑战应答用同一 authKey 对称完成双向证明，是最小代价（1 round-trip，无额外密钥协商）。

### 2. 双端互拨 vs 单连接复用

**结论：单连接复用 + 指纹字典序主从裁决（字典序小者主拨），避免双连。**

两台 DM 互相有对方地址时，若双方都主动拨号会建两条连接（A→B 出站 + B→A 出站），浪费且在线状态语义混乱。裁决规则：**`myFingerprint < peerFingerprint` 者主动拨**（指纹是 12 hex 字符，[`pairing.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/remote/pairing.ts) L88/L100 `sha256(publicKey).slice(0,6)` hex），字典序小者主拨（拨号方），大者只监听入站不主动拨（监听方）。

**双向在线感知靠单连接复用**：A 主拨 B 成功（含 sync.hello 互认完成）→ A 侧 OutboundClient 连接存活 = B 在线（A 知道 B 在线，出站 presence）；B 侧 `RpcServer` 入站注册表里有 A 的 PASETO 连接 = A 在线（B 知道 A 在线，入站 presence，命门 2 新增）。一条出站连接承载双向在线感知 + 双向 sync 通道。

**去重**：OutboundClient 启动时遍历 PairingStore 已配对设备，仅对 `myFingerprint < peerFingerprint` 的设备拨号；对 `myFingerprint > peerFingerprint` 的设备跳过（等对方拨我）。若两端同时启动且互拨（裁决前），后建连的一方在 sync.hello 后检测到已有同指纹的存活连接则主动关冗余连（保险，正常情况字典序裁决已避免）。

### 4. ping-pong 终止性（一审命门 3 重写同步职责模型）

**结论：单连接一致化——拨号方双职责（push+pull），监听方纯被动；收敛终止性由「对端回灌数据 id 全重合 → hasChange=false → 不再 onDirty」保证；冗余 pull/push 有界。**

**同步职责模型**（一审命门 3 修订，删除原「rpc.broadcast 天然通知对端」错误表述——对拨号方不成立，因为拨号方本端 clients 无对端连接）：

| 角色 | 本地脏数据 | 收到对端通知 |
|---|---|---|
| 拨号方（myFp < peerFp） | 经出站连接 `callRpc(peer, 'sync.push', payload)` 主动推 | OutboundClient 收到对端 `sync.dirty` notify → `callRpc(peer, 'sync.pull')` 拉 |
| 监听方（myFp > peerFp） | `rpc.broadcast('sync.dirty')` 通知所有入站客户端（含拨号方的出站连接） | 收到拨号方 `sync.push` → `mergeRemoteSession`（`hasChange=true` 时经 `onMergedRemote` 回调广播 `chat.event synced`，小项 7e 双路径）；收到拨号方 `sync.pull` 请求 → 返回数据 |

**SyncCoordinator.onDirty 拓扑分流**（两端跑同样逻辑，角色由拓扑决定）：
```typescript
onDirty(sid):
  // 监听方职责：广播 sync.dirty 给本端入站客户端（拨号方作为入站客户端会收到）
  rpc.broadcast('sync.dirty', { sessionId: sid, cursor })
  // 拨号方职责：对每个本端拨号的对端，主动 push 脏数据
  for peerFp in outbound.dialedPeers():
    batches = chat.buildPushBatches(sid)  // 按 512KB 切多批（见下「push 载荷分批」）
    for batch in batches:
      outbound.callRpc(peerFp, 'sync.push', { sessionId: sid, payload: batch })
```
- 监听方的 push 部分是 no-op（没拨任何对端，`outbound.dialedPeers()` 为空）
- 拨号方的 broadcast 部分对对端无效（拨号方本端 clients 无对端连接），但有效通知本端渲染进程（local 客户端）
- **push 载荷分批（消除 >1MB 死区）**：`sync.push` 单次 1MB 限制（[`sync/rpc.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/sync/rpc.ts) L18-20）由 `buildPushBatches` 在源头切分规避——`ChatStore.buildPushBatches(sid, maxBytes = 512 * 1024): PushPayload[]`：序列化 ≤ maxBytes 时单批（与现设计等价）；超限时按 `createdLocallyAt` 升序把 messages 切多批（每批 ≤ maxBytes），markers + session 放最后一批（锚点消息先落地，减少瞬时 orphan；即使乱序 arrival 也由 M3b orphan 隔离/脱孤机制兜底，[`chat-store.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/store/chat-store.ts) L188-211 orphan→sync_orphan_markers + 脱孤检查）。单条消息自身超限的极端情形跳过并留日志（M2a 卸载机制已把工具输出限幅，此情形理论罕见），申报为一期已知边界。`pushToPeer` 顺序推各批；中途断线 → 重连后整会话重推（`INSERT OR IGNORE` 幂等，安全）。
- **分批正确性与终止性论证**：
  - **收敛结果一致**：分批到达与一次到达收敛结果一致——`mergeSession` 三路去重以 id 为准（[`merge.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/sync/merge.ts) L29-36）+ orphan 脱孤机制（M3b 评审命门 2，[`chat-store.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/store/chat-store.ts) L205-211）保证乱序 arrival 也能正确收敛；`INSERT OR IGNORE` 幂等使重推安全
  - **冗余 pull 有界**：中间批次引发对端多次 onDirty 由监听方 `SyncCoordinator` 既有 200ms debounce 合并为一次广播（[`coordinator.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/sync/coordinator.ts) L29/L35-39 debounceMs），拨号方冗余 pull 次数 ≤ 批次数有界
  - **带宽成本申报**：全量推送（每次变更推整会话）一期 LAN 场景申报接受；天真 cursor 增量（`afterTs` 过滤）因跨设备时钟偏移不可靠列非目标并注明（见非目标段）

**收敛终止性走查（A 拨 B，A 写消息 M1）**：
1. A `appendMessage(M1)` → A onDirty → A `SyncCoordinator.onDirty`
2. A 拓扑分流：broadcast（本端无远程客户端，no-op）+ push M1 给 B（`callRpc(B, 'sync.push', {M1})`）
3. B 收到 `sync.push` → B `mergeRemoteSession({M1})`（M1 在 B 不存在 → mergedCount=1 → hasChange=true）→ B onDirty → B `SyncCoordinator.onDirty`
4. B 拓扑分流：broadcast `sync.dirty` 给本端入站客户端（A 的出站连接在 B 的 clients 里 → A 的 OutboundClient 收到 notify）+ push（B 是监听方，无拨号对端，no-op）
5. A 收到 B 的 `sync.dirty` notify → A `callRpc(B, 'sync.pull')` → A `mergeRemoteSession`（B 的数据 = M1，A 已有 M1，id 全重合 → mergedCount=0 → hasChange=false）→ A **不** onDirty → 链路终止

**冗余 pull 有界性论证**：
- 第 5 步 A 的 pull 是冗余的（B 的 M1 来自 A 的 push），但 `hasChange=false` → 不再 onDirty → 不再 push/broadcast → 终止
- **并发写入场景**（A 写 M1 同时 B 写 M2）：
  1. A push M1 给 B → B merge M1（新）→ B onDirty → B broadcast sync.dirty → A pull from B（B 有 M1+M2，A 只有 M1）→ A merge M2（新）→ A onDirty → A push（A 有 M1+M2，B 已有 M1+M2）→ B merge（id 全重合，hasChange=false）→ 终止
  2. 同时 B broadcast sync.dirty → A pull（B 有 M1+M2）→ A merge M2（新，与上面并发的 A onDirty 合并去重）→ A push 给 B → B merge（全重合）→ 终止
- 每轮并发写入产生 **有界的 2 次额外 round-trip**（A→B push + B→A pull，或 B→A notify + A→B pull），之后 id 全重合必然 `hasChange=false` 终止

**关键不变式**：`mergeSession` 三路去重以 id 为准（[`merge.ts`](file:///c:/Users/24739/Downloads/openminis1/deskminis/src/minisd/sync/merge.ts) L29-36，id 重复保留 local）——对端从本端 pull/push 走的消息 id 与本端完全重合，回灌时 id 全部命中 `byId`，新增 0 条；marker 同理（LWW 裁决后值相同则无更新，必改 6 精化）。故第二轮回灌必然 `hasChange=false`。

**专项测试**（Task 6）：双实例 in-process 互连静默期内（双方各写一轮 → 双向收敛完成 → 等待 2s）`sync.dirty` 广播计数 + `sync.push` 调用计数不再增长（防 ping-pong 实证，小项 7a in-process 才能 hook broadcast）。

### 6. 心跳/保活参数

**结论：WS ping/pong 标准心跳（30s ping / 60s 判死）+ 断线指数退避重连（1→2→4→8→16→30s 上限）。依据如下，不拍脑袋。**

- **ping 间隔 30s**：ws 生态常见实践（`reconnecting-websocket` 默认值等）推荐 ping 间隔 < 30s（避免主流代理 60s 空闲超时断连）；出站 PASETO 60s 短 TTL（决策 1）内至少 2 次 ping（30s 间隔），足够检测死活；ws 库原生 `ws.ping()` + `ws.on('pong')` 是 RFC 6455 标准心跳帧，不占应用层消息
- **判死 60s 无 pong**：2 倍 ping 间隔，容许一次 ping 丢失；判死后 `ws.terminate()` 触发重连
- **重连退避 1→2→4→8→16→30s（上限 30s）**：指数退避 + 上限封顶，参考 ws 生态常见实践（`reconnecting-websocket` 库默认 1→30s）；首次失败 1s 快重试（瞬时网络抖动），后续指数增长避免狂拨，30s 上限保证最长半分钟恢复感知
- **不发明新协议**：WS ping/pong 是标准，不搞应用层 `sync.cursor` 心跳（M3b 评审命门 4 已移除应用层心跳，M3c 用传输层 ping/pong 替代）

```typescript
'remote.pair.join': async (p: {
  host: string;              // 对端地址 host
  port: number;              // 对端端口
  pairingCode: string;       // 对端 begin 出的 8 字码
  peerName?: string;         // 对端设备名（UI 显示用，可选）
  listenPort?: number;       // 本端监听端口（传给对端 complete，必改 4）
}, conn) => {
  assertAuthMode(conn, ['local'], 'remote.pair.join');
  // 1. 出站拨对端 ?pairingCode= 端点（pairing authMode）
  const ws = new WebSocket(`ws://${p.host}:${p.port}/?pairingCode=${p.pairingCode}`);
  await once(ws, 'open');
  // 2. 调对端 remote.pair.complete（传 myPublicKey/myFingerprint/myName/listenPort）
  const completeRes = await rpcCall(ws, 'remote.pair.complete', {
    pairingCode: p.pairingCode,
    peerPublicKey: service.myPublicKey,  // 本端公钥给对端（Uint8Array）
    peerFingerprint: service.myFingerprint,
    peerName: os.hostname(),
    listenPort: p.listenPort,
  });
  // 3. 从 complete 响应取对端公钥（免手抄），本地 sha256 截断 12 hex 重算指纹（防伪报）
  const peerPubKey = new Uint8Array(Buffer.from(completeRes.myPublicKeyB64, 'base64'));
  const recomputedFp = Buffer.from(sha256(peerPubKey).slice(0, 6)).toString('hex');
  // 4. 本端 joinPairing（封装 derivePairingKey + save + setAddress，私钥不离开 service）
  service.joinPairing(completeRes.myPublicKeyB64, recomputedFp, p.peerName ?? '未命名设备', p.pairingCode, `${p.host}:${p.port}`);
  ws.close();
  return { ok: true, peerFingerprint: recomputedFp };  // 返回重算值供 UI 展示人工比对
}
```

**authMode=local 理由**：join 是本端用户在 DevicesModal 点「加入」发起的，调用方是本机渲染进程（per-run token 连接，天然 local）；join 内部出站拨对端用的是 `?pairingCode=`（对端 pairing authMode），与本端 join 的 authMode 无关。

**指纹本地重算防伪报**：对端 complete 响应可以伪造公钥，但 join 侧不信任响应里的 `peerFingerprint`（complete 响应只返回 `myPublicKeyB64`，不返回指纹——join 侧从公钥本地 `sha256(pubKey).slice(0,6)` hex 重算）。这与 M3a 安全模型「指纹人工比对」一致——join 返回重算指纹供 UI 展示，用户与对端 DevicesModal 显示的指纹人工比对。

**PairingService.joinPairing 方法**（封装 derivePairingKey+save+setAddress，私钥不离开 service）：
```typescript
joinPairing(peerPubKeyB64: string, peerFingerprint: string, peerName: string, code: string, addr: string): void {
  const peerPub = new Uint8Array(Buffer.from(peerPubKeyB64, 'base64'));
  const key = derivePairingKey(this.identity.privateKey, peerPub, code, peerFingerprint, peerName);
  this.store.save(key);
  this.store.setAddress(peerFingerprint, addr);
}
```

**dial 流程**（决策 1 互认协议落地）：
1. `pairing.get(peerFp).authKey` + `encodePaseto({ exp: now+60s, iat: now, device_fingerprint: myFp, jti: randomUUID(), aud: peerFp }, authKey)` 铸 token
2. `new WebSocket('ws://<addr>/?paseto=<token>')`（noProxy，ws 库默认不读 HTTP_PROXY）
3. `ws.on('open')` → **不立即 onOnline**，先发 `sync.hello` RPC：`callRpc(peerFp, 'sync.hello', { nonce: randomHex(16) })`
4. 收到 `{ mac, listenPort }` → 本地算 `hmacSha256(authKey, 'm3c-hello'+nonce)` 比对 mac
5. 匹配 → `onOnline(peerFp)` + `setLastSeen(peerFp, nowEpoch())` + `setAddress(peerFp, sourceIp:listenPort)`（端口漂移自愈）+ 启动 ping interval + `ws.on('message')` 监听 `sync.dirty` notify
6. 不匹配 → `ws.terminate()` + 退避重连

**callRpc 实现**：在出站 ws 上发 JSON-RPC request（`{ jsonrpc:'2.0', id: ++reqId, method, params }`），维护 `Map<id, {resolve, reject}>` 等响应；超时 10s reject。`sync.hello` 是首个 callRpc，后续 `sync.push`/`sync.pull` 复用。

**sync.dirty notify 监听**：`ws.on('message', raw)` 解析 JSON-RPC，`method === 'sync.dirty'` 且无 `id`（notify）→ `onRemoteDirty?.(peerFp, params.sessionId)`。

**重连**：close/error 后按 `reconnectBackoffMs` 数组依次延迟重拨，数组耗尽后固定 30s 重试。重拨前重铸 PASETO（旧 jti 已见缓存会拒，必须新 jti）。

**ping/pong**：sync.hello 通过后启动 `setInterval(pingIntervalMs)` 发 `ws.ping()`；`ws.on('pong')` 重置计时器；`pongTimeoutMs` 内无 pong → `ws.terminate()` 触发重连。`unref()` 计时器。

**PASETO 重铸**：出站 TTL 60s，连接存活期间在 ping 周期里检测 token 将过期（>50s）则主动 close 触发重连重铸（新 jti）。
