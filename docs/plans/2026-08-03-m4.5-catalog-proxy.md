## 1. 动机与根因链

M4 复核时 dry-run 真实输出暴露了一条完整的失效链。复核方已实测取证，以下作为设计前提，**不重新论证**：

```

  → models.dev 拉取直连 → 超时 → catch 静默吞（model-catalog.ts L69）
  → models-dev-cache.json 从未被写入（复核方确认该文件在用户数据根中不存在）

  → 后果 A：ContextPolicy 回退 FALLBACK_WINDOW=32000（context-policy.ts L6, L31）
           → 落入「>=32K 且 <64K」档位（context-policy.ts L44-47）
           → 只 offload 不 compact → 长对话无限增长
  → 后果 B：clampThinkingLevel 见 !info 即把 thinking 永久钳到 'off'（model-catalog.ts L88-93）
           → 支持推理的模型也开不了
```

- [x] **Step 2: 实现 createProxyFetch**

在 `model-catalog.ts` 顶部新增导出函数（不动 ModelCatalog 类，不动 refresh 逻辑，只新增装配工具）：

```typescript
import { ProxyAgent, fetch as undiciFetch } from 'undici';

/** 代理环境变量优先级：HTTPS_PROXY > HTTP_PROXY > ALL_PROXY（大小写各查一次）。 */
export function createProxyFetch(): FetchLike | undefined {
  const proxyUri =
    process.env.HTTPS_PROXY || process.env.https_proxy ||
    process.env.HTTP_PROXY || process.env.http_proxy ||
    process.env.ALL_PROXY || process.env.all_proxy;
  if (!proxyUri) return undefined; // 无代理 → 用默认全局 fetch（直连）
  // NO_PROXY 尊重：models.dev 命中则直连
  const noProxy = process.env.NO_PROXY || process.env.no_proxy;
  if (noProxy) {
    const domains = noProxy.split(',').map(d => d.trim().toLowerCase()).filter(Boolean);
    if (domains.includes('*')) return undefined; // 全部直连
    // models.dev 域名匹配（精确或后缀）
    if (domains.some(d => d === 'models.dev' || 'models.dev'.endsWith(d))) return undefined;
  }
  const agent = new ProxyAgent(proxyUri); // 仅此一处实例化，不 setGlobalDispatcher
  return async (url: string, init?: Parameters<typeof fetch>[1]) =>
    undiciFetch(url as Parameters<typeof undiciFetch>[0], { ...init, dispatcher: agent });
}
```

**关键**：`ProxyAgent` 实例仅在 `createProxyFetch` 闭包内创建，返回的 fetchImpl 闭包持有 agent 引用。**不调用 `setGlobalDispatcher`**。该 fetchImpl 只传给 `ModelCatalog` 构造函数，仅作用于 `refresh` 这一个调用点。

**数值与来源**（一手数据：复核方 2026-08-03 直接拉取 models.dev/api.json 全量 6043 条并按族聚合，非二手报道）：

| 模型族 | 正则 | contextWindow | thinking | 一手分布（models.dev 实测） |

| qwen | `/^qwen/i` | 128_000 | false | 487 条（含 qwen3.x，见下方顺序说明）；`reasoning:true` 238/487（49%，真实分歧）。本条只兜底 qwen1/2/-max/-plus 等旧代（qwen3.x 由上方 `/^qwen3/i` 先中先赢截获），旧代推理支持不稳定，保守 false |

**方法论更正（复核方自查）**：本表初稿标注「保守取下界」，但一手分布显示各族真实下界为 **0 / 1024 / 8000**（早已退役的玩具型号），照该原则填会把模型打进 `<32K` 的 **none 档——完全不管理上下文**，比现状更糟。故实际采用的原则是：

> **取该族「当代在售主力型号」的窗口下界，且硬性不低于 128K。**

理由三条：
1. BUILTIN 只在 **models.dev 与 basellm 双源皆失败**时才兜底（Task 1 修好后极少触发），其精度重要性远低于「落在哪个档位」；
2. 填过高 → 上下文超限是**硬失败**（API 直接拒绝请求）；
3. 填过低 → 落进 `<32K` 的 none 档（完全不管理）或 32K–64K 陷阱档（只 offload 不 compact），是**静默劣化**，更难发现。
128K 恰好落在 `>=64K` 档（offload + compact 俱全），是五族的安全交集。

**顺带发现（不扩范围，仅记录供决策）**：现存 `/^qwen3/i` 条目（L20，128K）会截获 `qwen3.5` / `qwen3.6` / `qwen3.7` / `qwen3.8` 等当代型号，而这些型号一手实测为 **262144 ~ 1000000**，128K 是显著低估，会导致当代 Qwen 用户过早压缩。**本里程碑不改**（超出 Task 2「补五族」范围，且 Task 1 修好后该条目基本不触发），但建议执行方在计划评审时确认是否顺手提高——**若改必须单独申报为偏差**。

  setManualOverride(modelId: string, window: number | undefined): void {

**理由**（双面论证）:

**支持提高**：
1. **2026 年主流模型 ≥128K**：claude 200K、gpt-4 128K、gpt-5 400K、gemini 1M、glm/grok/kimi 128K（Task 2 新增 BUILTIN）。未知模型大概率是大窗口模型，32K 回退严重低估。

### 决策点 3：手动 contextWindow 在 clampThinkingLevel 上的体现

**结论**：手动 contextWindow **只影响 `getModelContextWindow`**（优先级最高），`clampThinkingLevel` **不变**（仍走 `lookup`，不查手动值）。

**理由**：
- 手动值只有窗口（number），没有 thinking 标记——用户配 contextWindow 是为了修 offload 陷阱，不一定知道 thinking 支持
- `clampThinkingLevel` 仍走 `lookup`（models.dev 缓存 > BUILTIN），若该模型族在 BUILTIN 表中（Task 2 已补主流族），thinking 走 BUILTIN 标记
- 若该模型 BUILTIN 也没有（完全未知），`!info` 钳 off（既有行为不变）——保守正确，用户不知道窗口大概率也不知道 thinking
- 用户想开 thinking 的正途：等 models.dev 目录更新（Task 1 修好代理后）或补 BUILTIN（Task 2 已覆盖主流族）
- **最小改动原则**：clampThinkingLevel 逻辑一字不动，手动值只作用于窗口查询

**边界场景验证**：
- `glm-4.5` 手动配 contextWindow=200_000 → `getModelContextWindow` 返回 200_000（手动优先）；`clampThinkingLevel` 走 BUILTIN `/^glm/i` thinking:true → 透传 high ✓
- `mystery-model` 手动配 contextWindow=64_000 → `getModelContextWindow` 返回 64_000；`clampThinkingLevel` lookup 返回 undefined → 钳 off ✓（保守）

### 决策点 5：代理环境变量的读取口径

**结论**：

| 变量 | 读 | 优先级 | 说明 |
|------|----|----|------|
| HTTPS_PROXY | 是 | 1（HTTPS 资源优先） | models.dev 是 HTTPS，主要用此 |
| https_proxy | 是 | 1（小写等价） | POSIX 兼容（Linux 大小写敏感） |
| HTTP_PROXY | 是 | 2 | HTTPS 资源的回退代理 |
| http_proxy | 是 | 2（小写等价） | POSIX 兼容 |
| ALL_PROXY | 是 | 3 | 通用回退（curl 惯例） |
| all_proxy | 是 | 3（小写等价） | POSIX 兼容 |
| NO_PROXY | 是 | — | 域名匹配则直连（逗号分隔，精确或后缀匹配，`*` 全直连） |
| no_proxy | 是 | — | 小写等价 |

**口径依据**：curl / Node convention。Windows 环境变量大小写不敏感（process.env 自动归一），但 Linux/macOS 大小写敏感——同时查大小写确保跨平台一致。

**NO_PROXY 匹配规则**（简化，零新依赖用原生字符串操作）：
- 逗号分隔域名列表
- 精确匹配：`models.dev` == `models.dev` ✓
- 后缀匹配：`models.dev`.endsWith(`.dev`) ✓（注意：`models.dev`.endsWith(`dev`) 也 ✓，但 `evilmodels.dev` 也会匹配 `dev` ——这是 curl 的已知行为，本里程碑不改进）
- 通配 `*`：全部直连

**不读的变量**：`SOCKS_PROXY`（undici ProxyAgent 不支持 SOCKS，需 socks-proxy-agent 包——违反零新依赖红线）。

### 决策点 6：双源优先级与 basellm 多 vendor 冲突消解（配合 Task 7）

**结论 A — 源优先级**：**models.dev 主源，basellm 备源**，串行降级（主源失败才拉备源），不合并两源数据。

理由：
- models.dev 提供**结构化数字字段**（`limit.context` / `reasoning` 布尔），无需解析、无歧义；basellm 的窗口编码在 `tags` 字符串里且同名多值，解析与消解都是额外失真面。
- 覆盖面实测相当（6043 vs 6185，glm/grok/kimi/minimax 两侧齐全），主源没有覆盖劣势。
- **不合并**：两源对同一模型可能给出不同值（如 glm-5.1：models.dev 200000，basellm 部分 vendor 202800），合并需要再定优先级规则，徒增复杂度且收益为零——串行降级已能保证「至少有一个源生效」。
- 代价是有代理的机器永远用不到备源（走主源即可），但备源的价值本就是**给没有代理的机器兜底**，串行降级恰好覆盖该场景。

**结论 B — 多 vendor 同名冲突**：**官方 vendor 优先，无官方则取该模型名下的最小值。**

- 官方判定：`vendor_name` 命中该模型的原厂（如 `glm-*` → `Zhipu AI` / `Z.AI`）。实测 glm-5.1 两个官方 vendor 均报 **200K**，与 models.dev 的 200000 **完全一致**——官方优先规则可用主源交叉验证，是它的正确性依据。
- 无官方时取最小值：转售商上报的 202.8K/204.8K 多为含系统开销的毛值，取最小避免超限（超限是硬失败，见 §4 方法论）。
- **不取众数**：众数无语义依据，且实测 glm-5.1 的 200K×9 vs 202.8K×8 仅差一票，不稳定。

**实现约束**：官方 vendor 映射表若要写死会成为维护负担，故**只对已知族写少量条目**（glm→Zhipu AI/Z.AI 等），未命中一律走「取最小值」——规则退化路径必须有测试。
