## 4. 七个 Task

### Task 1 — catalog 冲突消解规则精化（A6，最高优先）

**现状**：`mergeModelsDevEntry`（L163-170）两两折叠取纯最小，被单离群 vendor 拖垮（`glm-5.1` 被 `digitalocean` 的 163840 拖到低于官方 200000）。

**规则改为**：contextWindow / maxOutputTokens 取「被 **≥2 家 vendor 佐证过**的值中的最小者」；**全部值都只有一家报时退化为纯最小**。thinking 不变（任一为真，能力位）。

**实现形态（决策点 1 结论：先收集再一次性消解）**：
- 在 `tryFetchModelsDev` 内改为先收集 `Map<id, Array<{contextWindow?, maxOutputTokens?, thinking}>>`（每个 id 收集全部 vendor 的原始条目），再对每个 id 调一个新的纯函数 `resolveModelsDevConflict(entries)` 一次性消解。
- 理由：新规则本质是**全局性质**（需「值→报该值 vendor 数」的完整视角），折叠携带计数表会让结构纠缠、难以单测；先收集再消解把「收集」与「消解规则」解耦，`resolveModelsDevConflict` 是纯函数，可直接用注入假 fetch 单测（红线：单测禁外网）。
- 原 `mergeModelsDevEntry` 删除或降级为 `resolveModelsDevConflict` 内部辅助（建议删除，避免两套规则并存）。
- `resolveModelsDevConflict(entries)` 逻辑：
  1. 对 contextWindow、maxOutputTokens 各自：统计 `value → count`（count = **报该值的不同 provider 数**；undefined 值不参与）。**计数单位写死为「不同 provider 数」**——models.dev 结构下同一 provider 内同一 id 只出现一次，provider 数与 vendor 数两种口径当前等价，但不写死会给实现留歧义。
  2. 取 `count >= 2` 的值中的最小值；若无任何 `count >= 2` 的值，退化为全部值中的最小值；
  3. thinking = 任一为真。
- 与 vendor 迭代顺序无关（统计计数天然顺序无关）。
- **退化路径覆盖面**：复核方实测当前 models.dev 全量 2949 个 id 中 **2008 个（68.1%）只有单一 vendor**，全部走退化路径、行为与现状完全一致。实现者**不得**为单 vendor 做特殊处理——它们与「全单例退化」共用同一条纯最小代码路径，现状行为自动保持。
- **maxOutputTokens 套用同规则有独立必要性**：复核方实测 941 个多 vendor 模型中，contextWindow 分歧 452 个，**maxOutputTokens 分歧 524 个（比窗口分歧还多），其中 144 个是「窗口不分歧但 output 分歧」**。即 output 套用同规则不是顺手，是防高估的独立缺口。
- **basellm 侧（决策点 2 结论：不加佐证条件）**：`resolveBasellmConflict` 维持「官方 vendor 优先，否则取最小」。理由：a) basellm 的官方 vendor 命中时已有主导权，加佐证条件的结果大概率不变，改动收益≈零；b) basellm 仅当 models.dev 失败时作备源（罕见路径），任何行为变化都引入回归面；c) 官方优先路径依赖单个官方 vendor，与「≥2 佐证」概念不天然契合。仅补一条注释说明为何不加，不改行为。
- **MERGE_RULE_VERSION 1 → 2**（L177）：缓存按旧规则算出，必须作废（构造 L204 已按版本过滤，作废后下次 refresh 重拉）。

**测试（全部注入假 fetch，禁外网）**：
1. 单离群不拖垮：`glm-5.1` 场景——8 家报 200000 + 1 家报 163840 → 取 200000。
2. 全单例退化纯最小：每个值都只有一家报 → 取全局最小。
3. 与 vendor 顺序无关：同一组条目打乱顺序结果一致。
4. 佐证值中仍取最小：多家报 200000、多家报 1047576 → 取 200000。
5. 单独值 1 家、无 ≥2 佐证 → 纯最小（覆盖退化路径）。
6. thinking 任一为真不变。
7. `MERGE_RULE_VERSION === 2` 断言（guard）。
8. basellm 现有单测不动（行为未变）。

### Task 2 — sync.hello mac 改常量时间比较（A1）

**锚点**：`outbound-client.ts` L218 `resp.mac !== expectedHex`。

**改动**：改用 `crypto.timingSafeEqual`。两边先各自 `Buffer.from(hex, 'hex')`，**先比长度，长度不等直接返回 false（不抛）**，长度相等再 `timingSafeEqual`。`timingSafeEqual` 长度不等会抛，必须先比长度。

```ts
const expectedBuf = Buffer.from(expectedHex, 'hex');
const respBuf = Buffer.from(resp.mac, 'hex');
const ok = expectedBuf.length === respBuf.length && expectedBuf.length > 0
  ? timingSafeEqual(expectedBuf, respBuf)
  : false;
if (!ok) return false; // 伪造/中间人
```

**红线**：仅此一处比较逻辑。hello 协议、nonce 生成、退避、`resp.listenPort` 地址簿刷新（L219-228）全不动。

**导入**：`node:crypto` 导入行（L20）追加 `timingSafeEqual`，零新依赖。

**测试**：单测覆盖——正确 mac 通过 / 改一字节失败 / 长度不同（多一字节或少一字节）返回 false 不抛 / 空串处理。

### Task 5 — stable 缓存容量上限（A7 / 审计 R3）

**锚点**：`system-prompt.ts` L91-108 `createStableCache` 的 `Map` 只增。

**改动（决策点 3 结论：上限 64 条，插入序淘汰，零依赖）**：
- 加常量 `STABLE_CACHE_MAX = 64`（或构造可选参，默认 64）。
- `get` 时若 `cache.size >= 64`，先 `cache.delete(cache.keys().next().value)`（Map 迭代序即插入序，删最旧），再 `set`。
- **不做 get 时 re-touch**（即非严格 LRU，纯 FIFO 插入序淘汰）。理由见决策点 3。
- `invalidate(sessionId)` 逻辑不变（前缀删除）。

**定性升级（复核方实测，2026-08-08）**：`buildStableSegment`（`system-prompt.ts` L61-72）只是 3-4 次模块级常量字符串拼接，微秒级；stable 段跨轮次的字节一致性由**纯函数确定性本身**保证，不依赖缓存。**结论：该缓存几乎零收益，属残留设施**。本 Task 的 64 上限是**止血**（消除无界增长），不是性能优化——因此 FIFO 可能挤掉热会话条目这一点无实际代价（重建即 3 次拼接）。

**测试**：单测——插入 64 条后第 65 条触发淘汰最旧；被淘汰条目的 `stableCacheKey` 键不再命中；invalidate 仍按前缀清空；同键重复 get 命中不重复插入（size 不涨）。

## 5. 必答决策点

### 5-1. Task 1 实现形态 → **先收集再一次性消解**
- 折叠携带计数表需在 `mergeModelsDevEntry` 里维护一张「id → 值 → vendor 数」的旁路表，与折叠结果耦合，逻辑复杂且难单测。
- 先收集 `Map<id, entries[]>` 再对每个 id 调纯函数 `resolveModelsDevConflict`，消解规则与收集解耦，纯函数可直接注入假 fetch 单测（红线：禁外网），且天然满足「与 vendor 顺序无关」与「≥2 佐证」的全局语义。

### 5-2. basellm 是否加佐证 → **不加**
- 官方 vendor 命中时 `resolveBasellmConflict` 已有主导权（取官方值），加佐证条件大概率结果不变，收益≈零。
- basellm 仅作备源（models.dev 失败才走），任何行为变化都引入回归面。
- 仅补注释说明为何不加，行为零改动，现有 basellm 单测不动。

### 5-3. Task 5 上限值与淘汰策略 → **64 条，插入序淘汰（FIFO），不 re-touch**
- 工作集分析：stable 缓存键 = `sessionId + modelId + bridgeGranted + config`。单用户场景会话数个位数，每会话每模型每授权态各一条；64 条远大于实际工作集，可兜住极端（多会话 × 多模型 × 授权态切换）。
- 每条是若干 KB 的 stable 提示段字符串；64 条内存占用可忽略。
- 淘汰策略：FIFO（删 Map 首键）足够——**该缓存几近零收益（见 Task 5 定性升级），加 64 上限是消除无界增长的止血，不是性能优化**；stable 段重建成本仅是 3 次字符串拼接，命中率非关键，FIFO 可能挤掉热会话条目因此无实际代价。**零新依赖**（不引 LRU 库）。
- **新增 backlog**：评估直接删除 `StableCache`——删除可彻底消除无界增长、去掉 `invalidate` 复杂度与整个 `StableCache` 接口，代价仅为每轮 3 次字符串拼接。**本里程碑不做**（涉及 M4 Task 2 的接口设计与 `loop.ts` 接线，改造面比止血大），但记录在案，避免后人误以为它是性能设施而不敢动。

### 5-4. Task 6 消除 vs 维持豁免 → **维持豁免**
清单级论证：
1. **输入面**：`v-html` 绑定 `inner = computed(() => PATHS[props.name] ?? PATHS.info)`，`props.name` 仅作静态字典字符串键，无任何用户输入/外部数据流可达字典值。
2. **内容面**：`PATHS` 是编译期 const 字面量，全部为受控线性描边 SVG（`path`/`rect`/`circle`/`ellipse`），无子元素、无事件属性、无可执行内容。
3. **威胁模型**：XSS 需攻击者控制的字符串到达 `v-html`；当前无此路径，风险为理论性。
4. **消除成本**：非 `path` 元素（`rect`/`circle`/`ellipse`）改 `path d` 需做弧线数学转换，涉及实测 **9/26** 个图标（sidebar/stop/clock/alert/memory/info/gear/panel/copy），视觉回归风险高且该组件全 UI 复用。
5. **兜底**：补白名单守卫测试，把「零用户输入」固化为测试红线（防未来误引入动态绑定）。

结论：收益/风险比不值得消除，维持豁免并以守卫测试固化。
