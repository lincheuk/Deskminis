# F11A 附件同步

消息里引用的附件随会话同步到已配对的设备。本文是实现之后的规格：协议、状态、限额、边界与未验证项。
代码在 `deskminis/src/minisd/sync/attachments/`，两端共用的名字校验与状态文案在 `deskminis/src/shared/attachments.ts`。

本文取代 `2026-07-31-m3-sync-design.md` 里设想的 `GET /attachments/:sha256`（HTTP 侧通道）：附件不另开端口、不走 HTTP。

## 1. 模型

- **逻辑身份是（会话，文件名）**。文件名是 `mediaRef.relativePath` 去掉 `attachments/` 之后的单层名字。消息里的引用不改写，
  接收端的文件落在它自己数据根的 `sessions/<会话>/attachments/<文件名>`，请求构建与预览按本机数据根解析，所以两台设备的数据根不同也能读到。
- **内容身份是 sha256 + 长度**，记在设备本地的表 `sync_attachments` 里（一个（会话，文件名）一行；不上线路）。
  行的状态：`present`（本机有完整且校验过的文件）、`missing`（知道内容身份，本机没有）、`failed`。
- **只同步被本机消息引用到的附件**。附件桶里的截屏、卸载的工具输出、工作区文件、记忆、设置、API Key 都不在其中；
  发送源按「消息引用 + 已登记 + 内容与登记相符」授权，不按「桶里有这个文件」授权。
- **未完成的字节只在 `<数据根>/sync-incoming/`**（`<sha256>.<长度>.part`）。附件桶里从不出现部分文件。
  收齐后整文件重算 sha256，相符才以不覆盖的方式（硬链接，目标已存在即失败）放到最终名字；行变成 `present` 只有这一条路和本机登记（同样先算哈希）。

## 2. 协议（附件协议第 1 版）

只走现有的加密通道（`?ch=1` 握手后的逐帧加密连接）上的 JSON-RPC。能力位 `attachments` 登记在 `sync/wire.ts` 的 `SYNC_CAP`，
在 `sync.hello` 里声明；`SYNC_PROTOCOL_VERSION` 不变。对端不声明就是不可用，不降级、不走别的通路。协议以后有不兼容的修订，换一个新的能力位名字。

一对设备里只有持有出站连接的一端（拨号方）能发请求，所以全部由拨号方发起；监听方有需求时发既有的 `sync.dirty` 通知，拨号方在同一条连接上重发清单。

| 方法 | 入参 → 返回 |
|---|---|
| `sync.att.manifest` | `{ v:1, sessionId, entries:[{name,size,sha256,mimeType}] }` → `{ v:1, entries, want:[{name,sha256,offset}], rejected:[{index,code}], indexing }`。请求方报自己有的；应答方回自己另有的（请求方用 get 取）与自己要的（请求方用 put 送，`offset` 是续传起点） |
| `sync.att.get` | `{ v:1, sessionId, name, sha256, offset }` → `{ v:1, offset, size, data }` |
| `sync.att.put` | `{ v:1, sessionId, name, sha256, offset, data }` → `{ v:1, offset, done }` |

- 线上只有文件名与内容身份，**没有任何路径字段**。文件名两端都过同一份校验（ASCII 单层名字，不含 `..`、盘符、备用数据流、Windows 保留设备名、结尾的点）。
- 块界固定：`offset` 是 256 KiB 的整数倍，每块恰为 `min(256 KiB, 剩余)`；`data` 是规范的标准 base64。应答必须正是请求的那一块。
- 三个方法的处理器开头顺序固定：加密通道上的 remote 连接（否则 `ATT_CHANNEL_REQUIRED`）→ 对端声明了能力位（否则 `ATT_CAP_REQUIRED`）→ 未关停 → 未暂停（否则 `ATT_PAUSED`）。
  装配处另包业务守卫，每次调用复查配对。错误只回 `ATT_*` 码与数字，不含路径与对端自报的内容。
- `rejected` 的码：`bad_entry` `bad_name` `too_large` `quota` `name_conflict`（重发同一份清单结果不变），`session_unknown` `not_referenced` `held` `failed` `busy`（应答方那边之后会变，请求方这一轮不记收敛）。

本机方法（只许本机连接）：`attachments.status`、`attachments.retry`、`attachments.cancel`、`attachments.read`；通知 `attachments.changed { sessionId }`。

## 3. 行为

- **续传**：传输被打断（含出站连接约每 30 秒的主动重拨）后暂存保留，重连后从暂存长度截到块界处继续。
- **重复块**不写盘；偏移不对、块长不对一律拒绝；任何写入都不可能越过声明长度。
- **损坏**：整文件校验不过 → 删暂存、不发布；自动从头再取一次，再不过记 `failed/hash_mismatch`，等用户重试。
- **去重**：暂存按内容键存，一份内容只传一次；本机别处已有同内容的完成文件时本机复制，不走网络。落盘仍是每个会话一份。
- **同名**：不同会话各在各的桶里。同一会话里同名但内容不同——本机先有的为准，不覆盖；后到的声明记成冲突，对端得到 `name_conflict`。
- **暂停**（设备页的暂停同步）：**附件收发全停**——不发起、三个对端方法回 `ATT_PAUSED`、在途的票当场撤掉、提交前也查。暂存保留，恢复后续传。
  这比消息的现行口径严（消息是「暂停方不发起、照常收下」）。若要改成与消息一致：去掉 `engine.ts` 里 `enter()` 对 put 的暂停判断与取回循环（`live()`）、`publishBlock()` 里的暂停判断，
  `tests/att-sync-engines.test.ts` 的「传输中途暂停收端」一例随之反转。
- **取消配对**：取消的这一端不再有块被写盘、不再有文件被发布（含本机去重）、不再有块被送出。没有取消的那一端不会被通知：对方取消之前已经发出的那一帧它会照常写下，之后连接断了就不再有新块。
  暂存保留（不经整文件校验不会被发布），7 天后清掉。已经到齐的文件不动。
- **关停与重启**：关停时撤掉全部票、保留暂存。启动时清掉 `.stage`、无主或过期的 `.part`、已不存在的会话的行（不删附件桶里的文件）。
- **本机文件变化**：登记后被改写的附件记 `failed/local_changed`，不再向其它设备提供；被删掉的记 `missing` 并催对端重传。
  认文件用 `lstat`：被引用的名字是符号链接（或登记后被换成符号链接）时不算普通文件，不登记、不送出。
- **本机删除会话**：删掉之后当场生效（不用等重启）——这个会话的附件不再向对端提供（`sync.att.get` 回 `ATT_NOT_FOUND`）、
  不再受理写入（在途的 `sync.att.put` 下一块回 `ATT_CANCELLED`）、收满的也不再发布。做法是每次查「消息引用」之前先问会话还在不在，
  不在就当作没有任何引用。`sync_attachments` 里这个会话的行留到下次启动自检才清，附件桶里的文件不删。

## 4. 限额

| 限额 | 值 | 超出 |
|---|---|---|
| 单个附件 | 32 MiB | `不可用：超过 32 MB 上限`，不传；本机超限文件本机照常可用 |
| 每会话附件总量 / 个数 | 512 MiB / 512 个 | `不可用：这个会话的附件已到上限` |
| 单块 | 256 KiB | 请求被拒 |
| 整文件校验失败后的自动重试 | 1 次 | `同步失败：内容校验不通过`，手动重试清零 |
| 应用内预览 | 8 MiB | 不带内容，提示用系统应用打开 |
| 暂存保留期 | 7 天 | 启动自检时删除 |

单文件上限与块长是协议常量，发布后再改要换能力位名字。

## 5. 界面状态

`attachments.status` 的每一项有两个独立结论：本机有没有这个文件（`localAvailable`，决定能不能打开、模型读不读得到），与同步状态：
就绪、传输中、未同步（本机已暂停 / 没有已配对设备在线 / 对方暂停了同步 / 等待同步 / 传输中断会自动续传）、未下载（用户取消过）、
同步失败（内容校验不通过 / 对方的应答不合规 / 写入本机磁盘出错 / 本机已有同名但内容不同的文件 / 本机文件被改动）、
不可用（对方的版本不支持附件同步 / 在线的设备上没有这个文件 / 超过上限 / 引用的文件名不合规）。
能重试的状态 chip 右侧有「重试」，被取消过的是「下载」，在途的是「取消」。

- **「取消」只在有东西可取消时给**：对端的清单已经告诉本机这份内容是什么（有一行、还要取）——传输中，或等待 / 中断。
  消息刚到、这个会话的清单还没交换时（「等待同步」，还没有行）没有按钮：那时取消记不下任何东西，清单一到照样会下载。
  清单到了之后按钮才出现。
- **「在线的设备上没有这个文件」只在问过之后下结论**：本机还没有行的附件，要等「这条引用出现之后」与每台在线设备各交换过一次清单、
  它们仍没列出它，才显示不可用；交换发生在引用出现之前（新消息刚到、带它的清单排在别的会话的传输后面）显示「等待同步」。
- **文件名不合规而文件就在本机**：`chat.prompt` 的附件白名单比同步的名字规则宽（允许以 `.` `_` `-` 开头、含 `..`、超过 128 字符；
  整条不分大小写，所以前缀写成 `Attachments/`、`ATTACHMENTS/` 它也收，并原样写进消息）。
  这类附件不同步，但请求构建按文件名读本机文件、模型看得到，所以状态里 `localAvailable` 为真，chip 显示「本机可用；文件名不合规，不同步到其它设备」，
  能打开，不提示「模型暂时看不到」。只认 `attachments/<单层文件名>` 这一种形态（前缀不分大小写，与白名单同一种比法）；
  多层目录、绝对路径等其余不合规引用仍按本机没有处理。前缀大小写不同的引用用的也是这句文案——它的文件名本身合规，不合规的是前缀的写法。
  同步侧只认全小写的 `attachments/`：这种引用在对端显示「不可用：引用的文件名不合规」，同一条消息里其余合规的附件照常同步。

## 6. 兼容

- 数据库追加一条迁移，只建新表。旧消息不改写，旧附件（`paste-<时间戳>.<扩展名>`）不改名，在第一次用到时登记。
- 新旧互通：旧构建不声明能力位，新构建对它一个 `sync.att.*` 都不发，附件显示「对方的版本不支持附件同步」；消息同步的线格式一个字段都没变。
- 新附件的文件名带内容哈希前 8 位（`paste-<时间戳>-<哈希>.<扩展名>`），两台设备不会各出一个同名异内容的文件。

## 7. 已知限制

1. 界面只能添加图片附件（单个不超过 5 MB）。文档等非图片文件的同步、哈希校验、打开都走同一条路，但没有产品入口（归 G03）。
2. 用户消息里引用的非图片文件在发给模型时仍被当作图片（既有的请求构建行为，本次没有改 `agent/loop.ts`）。产品界面不会产生这种消息；
   取证脚本注入的文档消息不要与还要继续提问的会话混用。
3. 附件到达之前就在接收端提问，模型看不到它（请求里是「附件已丢失」的占位文字）；chip 下有一句提示，发送不会被拦。
4. 同一会话里同名但内容不同的附件（两台旧版本设备在同一毫秒粘贴才会出现）后到的那份不同步，模型读到的是本机那份。
5. 已配对设备等同本机（既有边界）：它可以为缺失的引用提供任意内容并声明相符的哈希，也可以先推一条引用了桶里某个文件名的消息再取走那个文件。
   它做不到的是读写附件桶之外的任何东西、覆盖本机已有的文件、让未通过校验的内容被当作完成。
6. `sync.push` 不校验 `sessionId` 的形态（既有问题）。本次只在附件入口各自按 UUID 校验，没有改 `sync.push`。
7. 删除会话不清理已同步来的附件文件（清理规则归 F11B / F08，接口是 `AttachmentStore.referenced(sessionId)`）。
   删除目前也不传播：对端下次对账会把这个会话推回来，会话重新出现后它的附件照常同步。
   给 F11B：`referenced()` / `invalidRefs()` 已经在查缓存之前先问 `sessionExists`（装配处接的是 `chat.getSession`）；
   接入删除传播时仍须在删除、清除、恢复时调 `markDirty(sessionId)`，并在清库时删掉这个会话的 `sync_attachments` 行。
8. base64 多约三分之一流量；监听方只能靠拨号方的清单得知缺什么。
9. 清单交换之前不能取消：还不知道内容身份的附件（「等待同步」，没有行）没有取消按钮；小文件在清单到达后很快传完，来不及点。
   要做到「清单到达之前就能取消」需要一个不带内容身份的「不要取」标记，这次没有做。
10. 不合规的引用里，只有 `attachments/<单层文件名>` 这一种（前缀不分大小写）会按本机文件的有无如实显示；其余形态一律显示为本机没有，
    即使请求构建按文件名在桶里碰巧读得到同名文件：
    - 多层目录、绝对路径、反斜杠：`chat.prompt` 的白名单不收，只可能出现在对端同步来的消息里；
    - Windows 保留设备名（`CON.png` 等）、超过 255 字符的名字：过得了 `chat.prompt` 的正则，这里仍不认。`chat.prompt` 还要求桶里真有这个文件才收，
      而这样的文件用常规途径建不出来；真有的话状态会说本机没有，没有实测过。

    产品界面只产生全小写前缀的 `attachments/paste-…`，上面这些引用（连同前缀大小写不同的那一种）都只会来自直接调 RPC 的客户端或脚本。

## 8. 未验证项

1. **真实双 Windows**：开发机只有一台设备，下面的清单交 F12 执行。
2. 真实局域网上的吞吐；32 MiB 文件能否在一次约 30 秒的连接窗口内传完（传不完靠续传）。
3. 数据根不在 NTFS 上（硬链接不可用）时的发布回退：只有注入 `EPERM` 的单测。
4. 与旧构建真实二进制的互通：自动化用例用「不带能力位的 `sync.hello`、不注册 `sync.att.*`」的对端代表旧构建（两个方向各一例）；
   另用本任务之前的一份构建产物（含认证配对、不含 `sync.att.*`）与新构建在同一台机器上配对跑过一次界面验证：消息照常同步，
   附件显示「对方的版本不支持附件同步」。已发布的 0.1.x 安装包没有跑过。
5. 三台设备转供：只有存储层与单对交换的覆盖。
6. 断电后暂存文件尾部不可信的情形靠整文件校验兜住，没有实测。
7. **界面只在 Vite 开发服务器 + 无头 Chrome 里验证过**（真实的 `StageChat.vue` / `PreviewPane.vue` / chat store 连真实引擎，截图 9 张）。
   Electron 窗口里没有跑过，打包版里的预览没有验证。
8. **真实的符号链接没有验证**：开发机没有建文件符号链接的权限（`symlinkSync(…, 'file')` 得到 `EPERM`），
   `tests/att-store.test.ts` 里用真实符号链接的那一条在这台机器上是跳过（有权限的机器上会跑）。
   「认文件用 `lstat`」另有一条不需要权限的用例钉住（`tests/att-store-lstat.test.ts`：让 `lstatSync` 对指定路径回答「是符号链接」，
   `statSync` 与读写都是真的），它证明的是代码走 `lstat` 这一支，不是真实链接上的端到端行为。桶目录被换成 junction 的用例在开发机上是真跑的。
9. **杀毒软件或索引服务占用文件时的删除 / 改名重试没有实测**。有的只是注入抛错的用例：`retryBusySync` 的重试次数与放弃条件
   （函数直接抛 `EBUSY` / `EPERM` / `EACCES`）、`removeFileQuiet` 的返回值、登记时 `io.hash` 抛 `EBUSY` 的逐文件容错。
   没有任何用例在一个真实被别的进程占用的文件上跑过删除或改名。

### F12 双机清单

两台机器都设 `MINISD_HOST=0.0.0.0` 后启动并配对。

- **会话甲（只放文本与图片）**：A 发一句文本、粘贴一张图。B 上核对文本与图片，两端各跑 `certutil -hashfile <文件> SHA256` 比对；
  B 上点开图片；B 在会话甲里继续提问，让模型描述图片。
- **会话乙（另开一个，只放文档）**：用取证脚本经本机 token 调 `sync.push` 往会话乙注入一条带 docx 引用的消息，并把文件放进会话乙的附件桶
  （不是产品功能，不进产品补丁）。B 上核对哈希、打开文档。**两台设备都不在会话乙里提问**。
  取证脚本随交付附上（`f12-inject-attachment.mjs`，Node 22 及以上）：`node f12-inject-attachment.mjs --file <文件> [--data <数据根>]`，
  不给 `--session` 就新建一个会话；它拒绝把非图片文件注入到已经有过模型回复的会话，输出会话 id、附件名、sha256 与两端的 `certutil` 命令。
- 其余各项在会话乙里做（大文件同样靠取证脚本注入）：传一个 30 MiB 左右的文件，途中拔网线再插回；途中在任一端取消配对，确认文件没有出现；
  途中暂停任一端再恢复；一端换成不含附件同步的旧构建，确认消息照常、附件显示「对方的版本不支持附件同步」；
  Wireshark 过滤引擎端口，搜文件里的一段已知文字，应搜不到。
