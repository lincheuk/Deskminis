# F11C 认证配对（配对协议 v2）规格

状态：**实验性，默认关闭，未经独立密码学审查。** 默认配对方式仍是旧的明文配对（v1），README 里「配对那一步不加密」的说法对默认路径仍然成立。本文描述的认证配对只在用户在设备页显式打开开关的机器上发起。

术语：H = 显示配对码的一端（发起端）；J = 输入配对码的一端（加入端）；v1 = 旧的明文配对（`?pairingCode=` 加 `remote.pair.complete`）；v2 = 本文的认证配对；「不含认证配对的构建」= 基线提交 `9d0a32d` 及更早的构建。认证配对随 0.3.0 一起发出，识别对端是否支持只看同步握手里的 `pairV2` 能力位，不看版本号。

代码位置（路径省略 `deskminis/` 前缀）：

## 1. 威胁模型

### 1.1 资产与角色

- **配对码**：短秘密，只经 H 的屏幕由用户输入到 J。
- **配对记录** `PairingKey{authKey, sessionSecret}`：之后加密通道（`remote/channel.ts`）的长期根密钥。持有它就等同本机，能发消息、批准权限卡。
- **授权模型**：能看到 H 屏幕上配对码的人就是被授权者。本任务不改这一点。

### 1.2 攻击者与结论

| 攻击者 | 能力 | v1 现状 | v2 目标 |
|---|---|---|---|
| 被动窃听 | 录下配对全程 | 看得到配对码与两端公钥；派生密钥依赖静态私钥，暂未泄露 | 线路上只有 `pA`、`pB`、两端静态公钥、`name`、`listenPort`、`cA`、`cB`；配对码、`w`、`K`、`Ke`、派生密钥都不出现，不能离线穷举配对码 |
| 主动中间人 | 拦截、改写、丢弃、重放、注入全部帧；把 J 引到假 H | 看到码就能对两端各换一把公钥，两端都会无确认地落库 | 不知道码就无法让任何一端写入生效的配对记录；每次握手至多验证一个猜测 |
| 在线猜码 | 反复连 H 冒充 J | 每个升级请求是一次免费猜测，无上限 | 每个码最多 5 次握手，同一时刻 1 个；成功率不超过 5/31¹¹ ≈ 2×10⁻¹⁶（标记位不计入） |
| 重放 | 重放录下的帧 | 码一次性，握手无新鲜性 | 每次握手两端各取新的临时标量，旧确认值对不上新 transcript |
| 角色反射 | 把一端的帧弹回给它自己 | 无防护 | M ≠ N；身份串带角色标签；对端身份等于本机身份直接拒绝 |
| 协议降级 | 让一端改走明文路径 | 不适用 | 无带内协商；以标记开头的码只走 `?pair=2`，位数不足本地拒绝；`authenticated` 下 v1 入口全拒；v1 不能覆盖 v2 记录 |
| 本机网页 | H 本机浏览器里的任意网页可以连 `ws://127.0.0.1:<port>` | v1 要先知道码才能连上 | `?pair=2` 拒绝一切带 `Origin` 头的请求：网页耗不掉次数，也读不到握手里的静态公钥 |

不在防御范围：

- 看得到屏幕或配对码的人。
- 已被攻陷的任一端主机。
- 拒绝服务：同网段任何人都能占住握手槽位（连上不发帧，每次最多 10 秒，不扣次数）、用 5 次握手作废一个码，或直接阻断连接。不越权，界面给出明确结局。
- 不含认证配对的构建把 12 位码的前 8 位明文发出（§5 的烧码规则与残余）。
- 侧信道（JS BigInt 不是恒定时间）、流量分析。
- 静态公钥在握手里明文可见，是可关联的设备标识（与 v1 相同）。
- 身份只是声明：握手不证明静态私钥的持有（§3 第 9 条）。

本设计**不使用**任何传输层加密外壳，也不据此声称防中间人：防中间人的依据只有配对码经带外通道传递加上 PAKE 的密钥确认。

### 1.3 安全目标

- **G1** 配对码与派生密钥不上线路。
- **G2** 只有知道码的一方能完成配对，在线猜测限次。
- **G3** 双方静态身份、角色、双方临时份额、协议版本与套件、`name`、`listenPort` 全部进 transcript 或 AAD，任何一项被改则密钥确认失败。
- **G4** 验过对端的确认值之后才写配对记录，记录生效之后才可能获得业务访问。H 的记录写入即生效；J 的记录写入后只是暂存，收到 `done` 才生效，在那之前不能用来握通道，也不算已配对。
- **G5** 单次消费、过期（到点即清）、取消、限次。
- **G6** 确认失败、落盘失败、超时、取消，双方不留可用的业务权限：没有生效的记录，也没有挂着的连接。
- **G7** 无降级。

### 1.4 协议选择与出处

选 **SPAKE2，RFC 9382**（IRTF CFRG，Informational），套件 **`SPAKE2-P256-SHA256-HKDF-HMAC`**（RFC §6）。全部用仓库已装的 `@noble/curves`、`@noble/hashes` 实现，没有新增依赖，没有自创密码协议。

- 公开分析见 RFC 9382 的安全性考虑一节及其参考文献（Abdalla、Pointcheval，CT-RSA 2005；Abdalla、Barbosa、Bradley、Jarecki、Katz、Xu，CRYPTO 2020）。两篇的结论由审查者对照原文核对，本文不依赖对论文的转述。
- 不选 CPace：截至本文仍按草案对待，还需要 hash-to-curve。代价是 SPAKE2 依赖 M、N 的可信生成。
- 不选短认证串比较：要两端新增「核对并确认」的界面，安全性取决于用户真的去比；现有流程本来就让用户抄码，正好是 PAKE 的口令通道。

| RFC 9382 元素 | 实现 |
|---|---|
| 群 G = P-256，h = 1，生成元 P，阶 n | `p256.Point`、`Point.BASE`、`Point.Fn.ORDER`（`@noble/curves/nist.js`） |
| M、N（RFC §6） | `02886e2f97ace46e55ba9dd7242579f2993b64e16ef3dcab95afd497333d8fa12f`、`03d8bbd6c639c62937b04d997f38c3770719c629d7014d49a24b4f98baa1292b49` |
| 临时标量 x、y | 每次握手 `p256.utils.randomSecretKey()`，范围 [1, n-1]，不复用 |
| `pA = w·M + x·P`，`pB = w·N + y·P` | 编码为 65 字节未压缩点 |
| `K = x·(pB − w·N)` / `y·(pA − w·M)` | 相减结果为无穷远点则中止 |
| 群成员检查（RFC §7） | 长度恰为 65 且首字节 `0x04`，再 `Point.fromBytes`（不在曲线上抛错）与 `assertValidity()` |
| `len(x)` | 8 字节小端 |
| Hash / KDF / MAC | SHA-256、HKDF-SHA256、HMAC-SHA256 |
| MHF | scrypt |
| 确认值比较（RFC §7） | `node:crypto` 的 `timingSafeEqual` |

## 2. 协议 transcript

传输：`ws://<H 的 host:port>/?pair=2`，URL 不含任何秘密。帧是文本 JSON，键集必须恰好等于下表，多一个键、少一个键、类型或长度不对都算格式错。二进制字段用严格的 base64url（字符集合规、解码后长度精确、再编码等于原串）。

约定：J 是 SPAKE2 的 A（用 M），H 是 B（用 N）。`lp(x) = u64le(len(x)) || x`。`spkJ`、`spkH` 是各自的 32 字节 X25519 静态公钥。

**握手前（带外）**

- H 生成 12 位码：首位固定是标记 `0`，其余 11 位从 31 字符的字母表（不含 0、1、I、L、O）里拒绝采样。只显示在屏幕上，由用户输入到 J。
- 两端各自算 `w = OS2IP(scrypt(utf8(code), salt = utf8("DeskMinis/Pair/2/w"), N = 2^14, r = 8, p = 1, dkLen = 40)) mod n`。`code` 是归一化后的 12 个字符（大写、无连字符、首位是 `0`，标记位也在里面）。`w = 0` 时 H 重新生成码，J 报错。

**帧**

| # | 方向 | `t` | 其余字段 |
|---|---|---|---|
| M1 | J→H | `dm.pair.hello` | `v`: 2；`suite`: `"SPAKE2-P256-SHA256-HKDF-HMAC"`；`id`: b64u(spkJ，32B)；`name`: 字符串，UTF-8 不超过 64 字节，无控制字符，可空；`listenPort`: 0–65535 的整数，0 表示没有；`pA`: b64u(65B) |
| M2 | H→J | `dm.pair.reply` | `v`: 2；`id`: b64u(spkH，32B)；`pB`: b64u(65B)；`cB`: b64u(32B) |
| M3 | J→H | `dm.pair.confirm` | `v`: 2；`cA`: b64u(32B) |
| M4 | H→J | `dm.pair.done` | `v`: 2 |
| — | H→J | `dm.pair.fail` | `v`: 2。所有失败原因都是这同一串字节 |

**计算**（结构照 RFC 9382 §3、§4；身份串 A、B 与 AAD 的取值 RFC 留给应用，这里是本项目定的）

```
pA = wM + x·P                 (J，x 每次握手新取)
pB = wN + y·P                 (H，y 每次握手新取)
K  = x·(pB − wN)   (J)   =   y·(pA − wM)   (H)        差为无穷远点则中止
A  = utf8("DeskMinis/Pair/2/joiner") || 0x00 || spkJ
B  = utf8("DeskMinis/Pair/2/host")   || 0x00 || spkH
TT = lp(A) || lp(B) || lp(pA) || lp(pB) || lp(K) || lp(w)       pA、pB、K 为 65B 未压缩，w 为 32B 大端
Ke || Ka   = SHA-256(TT)                                        各 16 字节
ctx  = lp(utf8("DeskMinis/Pair/2/ctx")) || lp(utf8(suite)) || lp([0x02]) || lp(utf8(name)) || lp(u16be(listenPort))
AAD  = ctxH = SHA-256(ctx)
KcA || KcB = HKDF-SHA256(ikm = Ka, salt = nil, info = utf8("ConfirmationKeys") || AAD, L = 32)
cA = HMAC-SHA256(KcA, TT)          cB = HMAC-SHA256(KcB, TT)
```

**握手成功后的应用层导出**（RFC 之外，标准 HKDF 用法）

```
okm    = HKDF-SHA256(ikm = Ke, salt = nil, info = utf8("DeskMinis/PairingKey/v2") || ctxH, L = 64)
authKey = okm[0, 32)        sessionSecret = okm[32, 64)
roomId = base32(HKDF-SHA256(Ke, nil, utf8("DeskMinis/PairingKey/roomId/v2") || ctxH, 5))
对端指纹 = hex(SHA-256(对端静态公钥)[0, 6))        由 M1 / M2 的 id 本地计算，不单独传
```

**绑定关系**

| 被绑定的东西 | 绑在哪里 |
|---|---|
| 双方静态身份、角色 | 身份串 A、B（进 TT）；M 与 N 不对称 |
| 临时份额 | `pA`、`pB`（进 TT） |
| 配对码 | `w`（进 TT，并盲化 `pA`、`pB`） |
| 协议版本、套件、`name`、`listenPort` | `ctxH`：作为 RFC 的 AAD 进确认密钥，同时进配对密钥导出的 `info`。握手前还要对 `v`、`suite` 做严格相等检查 |

**顺序与落盘点**

1. J 收 M2，验 `cB`。不过就直接关连接，什么都不写，也不发 M3。
2. J 验过 `cB` 后先本机落盘，再发 M3。落盘失败就不发 M3，两边都没有记录。这次写入是**暂存**的：密钥已经在 vault 里，但本进程里读到的仍是写入之前的状态，新密钥不进通道候选，也不算已配对。
3. H 收 M3，验 `cA`。通过则先消费掉配对码，再落盘。H 的写入即时生效。
4. H 落盘成功回 `done`，失败回 `fail`。
5. J 收到 `done` 才让记录生效；收到别的、超时或断开，回滚自己刚写的记录，并关掉该指纹名下的入站与出站连接。

**三段式排列（`cB` 与 `pB` 同帧）与 RFC 的关系。** 主会话对照 RFC 9382 原文的阅读结论（**未经密码学专家审查**）：§3.1 的四条消息图明确称为示例流程（sample flow）；规范性要求在 §3.1 与 §3.3——双方都必须发送确认消息，A 在收到并验证 cB 之前、B 在收到并验证 cA 之前都不得认为协议完成；原文没有规定两条确认消息的先后，也没有禁止 cB 与 pB 同帧。所以三段式可以这样做，前提是：H 在发出带 cB 的那一帧时就把这次握手计为一次尝试（那一帧让对端可以验证它嵌在 pA 里的那一个猜测），并且 H 在验证 cA 之前不落盘、不授予任何业务权限。RFC §7 还要求：收到的点必须校验在群内（否则中止）、x / y 均匀随机且不得复用、点运算与比较不得泄露时间信息——确认消息的比较用常数时间比较；点运算的计时见 §3 第 8 条。

唯一消不掉的窗口：H 已落盘而 M4 在途中丢失，J 回滚，H 留下一条没有任何人持有密钥的记录（§6 残余 3）。

**测试向量。** `tests/spake2-rfc9382.test.ts` 逐字节对 RFC 9382 附录 B 的全部四组向量（身份 `server` / `client`、空 / `client`、`server` / 空、空 / 空；AAD 为空），期望值转录自 `https://www.rfc-editor.org/rfc/rfc9382.txt`（2026-10-03 读取），不是本实现算出来再写回的。向量之外的部分（带 AAD 的路径、身份串与 `ctx` 的编码、导出、帧）没有公开向量可对，只有自测（`tests/pair-proto.test.ts`）。

## 3. 未经独立密码学审查的部分

审查通过前 v2 不作为默认路径（§7）。

1. 协议与套件的选择：SPAKE2 而非 CPace 或短认证串；P-256 加 SHA-256，`Ke` 只有 128 位。
2. 消息排列与提交流程：`cB` 随 `pB` 同帧；J 先落盘再发 `cA`；J 的记录分「暂存」「生效」两段，生效由不认证的 `done` 触发。
3. 身份串与 `ctx` 的编码，绑定内容是否充分。
4. `w` 的派生：scrypt 参数、固定盐、40 字节取模。
5. 由 `Ke` 导出 `authKey`、`sessionSecret`、`roomId` 的 HKDF 标签，以及把 `ctxH` 放进 `info`。
6. 码长、字母表、标记位（12 位里只有 11 位随机）、5 次上限、300 秒有效期、每步 10 秒；烧码规则。
7. 帧格式、严格解析、统一失败帧、不认证的 `done` / `fail`。
8. `@noble/curves` 的 P-256 在 JS BigInt 下的计时侧信道；bigint 标量无法清零；该版本的公开审计范围未核实；锁文件 2.2.0 与实装 2.4.0 的差异。
9. 静态公钥只被绑定，没有私钥持有证明；指纹只有 48 位。知道码的一方可以声明任意公钥，包括一台已配对设备的公钥，从而顶替那条记录。知道码即已获用户授权，这不是越权，但意味着 v2 下的「指纹」是经过认证的声明，不是密码学身份证明。是否要加静态私钥的持有证明（例如把静态 DH 混进导出）属于在 RFC 之外自行组合，本实现没有做，留给审查者评估。
10. 对 RFC 常量 M、N 的离散对数未知这一假设的依赖；没有采用按用户派生 M、N。
11. RFC 向量只覆盖 AAD 为空的情形；带 AAD 的路径、导出、帧编码都没有公开向量可对，只能自测。
12. 范围外的提醒：配对后的加密通道（`remote/channel.ts`）是自研握手，仓库里没有独立审查记录。

另有一项请审核方确认的取舍：**J 按码格式跟随。** J 不需要自己打开开关——只要用户输入的是以 `0` 开头的完整 12 位码，J 就执行 v2（H 的用户已经显式打开）。这意味着 J 在 `legacy` 策略下也会执行未审查的 v2 代码。若要求两端都显式打开，把 `remote.pair.join` 里「v2 码 × legacy」一格改成本地拒绝即可（不发网络请求，不泄露码）。

## 4. 策略、限次与生命周期

- 本机配对策略 `legacy | authenticated`，存 `settings` 表键 `pairing.policy`，默认 `legacy`。不在网络上协商。
- `authenticated` 下：`remote.pair.begin` 出 v2 码；入站 `?pairingCode=` 一律 401；`remote.pair.complete` 抛 `PAIR_LEGACY_DISABLED`；J 输入 8 位旧码本地拒绝。
- 码的格式就是带外的版本信号：首位是标记且恰好 12 位 → v2；首位不是标记且恰好 8 位 → v1；其余一律本地拒绝（`PAIR_BAD_CODE_FORMAT`），不发任何网络请求。v2 失败不会改走 v1。
- 同一时刻只有一个 v2 码、一条握手在途；每个码最多 5 次握手。次数扣在任何用到 `w` 的计算之前、发出 reply 之前；格式不合规的帧不扣次数。握手期间连入的其它请求在升级阶段得到 401。
- 码结束的情形：验过 `cA`（单次消费）、取消（`remote.pair.cancel`）、次数耗尽、被新的码顶掉、策略切换、烧码、过期。过期有三道：到期定时器、查询状态时复查、每一帧处理前复查。
- 失败帧永远是同一串字节，不区分原因。
- `?pair=2` 连接不建 RPC 连接对象、不进广播名单、不计入站在线：握手未成功的连接调不了任何方法，收不到任何广播。
- v1 不得覆盖已有的 v2 记录（v1 的对端指纹是自报的）；要改回旧方式得先解绑。J 在发起旧的 8 位配对之前先按地址簿预检：目标地址名下已有 v2 记录就在本地拒绝，不发任何请求（§6 第 7 条）。
- **配对落定或撤回之后的连接处理。** 一条 v2 配对在某一端生效时（H 落盘；J 收到 `done`），这一端把该指纹名下现有的连接全部断掉：入站连接直接销毁套接字，不走关闭握手；出站连接断开。此刻还连着的都是用旧密钥握的，而业务调用只按指纹复查配对——记录被替换后该指纹名下仍有记录，只发 close 帧的话，一个不回 close 帧的旧密钥持有者在关闭超时（最长 30 秒）之前还能继续调业务方法。断不断不看「是否替换了旧记录」：那个判断取自提交时读到的旧值，凭据库读失败时会报成没有。随后按现在生效的密钥重建出站：J 总是拨；H 在替换了旧记录、或断之前出站在线时也拨（它原有的常驻重连循环被上面的断开一并摘掉了，不重拨的话，H 是拨号方的设备对在 J 重启后会一直离线到 H 重启；v1 的重新配对不拆这条循环）；首次配对时 H 不拨，与 v1 相同。J 在落盘之后失败并回滚时同样先断，该指纹仍有生效记录才重拨。

## 5. 新旧版本互通与烧码规则

| H ＼ J | 不含认证配对的构建 | 新版，输入不以标记开头 | 新版，输入以标记 `0` 开头 |
|---|---|---|---|
| 不含认证配对的构建 | v1 | 恰好 8 位：J 为 `legacy` 走 v1，J 为 `authenticated` 本地拒；其它长度本地拒 | 误输了完整的 12 位：旧 H 对 `?pair=2` 回 401，码没上线路。不足 12 位：本地拒 |
| 新版，`legacy` | v1 | 同上 | 没有 v2 码，401；不足 12 位本地拒 |
| 新版，`authenticated` | 旧 J 把输入截成 8 位明文发来：H 回 401 并作废该码（`PAIR_CODE_EXPOSED`） | 恰好 8 位且 J 为 `legacy`：当成 v1 码明文发出，H 回 401；它若等于 v2 码去掉标记后的前 8 位，H 同时作废该码 | 恰好 12 位：v2。不足 12 位：本地拒，无网络请求 |

烧码规则：v1 的明文入口（`?pairingCode=`、`remote.pair.complete`）上出现了当前 v2 码从第 1 位起的一段（8–12 位），或去掉标记位后从第 2 位起的一段（8–11 位），这个码当场作废。不相干的来码不作废（随机探测打不掉码，响应也永远是 401）。

残余两条：

1. **不含认证配对的构建的 J。** 它明文发出的 8 位里有 7 个随机字符。这个请求若被在途攻击者截下并阻断（没到 H，H 不知道要作废），攻击者还差 4 个随机字符（31⁴ ≈ 92 万）而只有 5 次机会，约 5×10⁻⁶。
2. **新版 J 自身。** 只要输入以标记开头，新版 J 不会把 v2 码的任何一部分放上网络。例外只有一种：用户漏掉了开头的 `0`，又恰好只输了 8 位，J 在 `legacy` 策略下把这 8 个随机字符当 v1 码明文发出。请求到达 H 时该码作废；被截下并阻断时，攻击者还差 3 个随机字符（31³ = 29,791），5 次机会约 1.7×10⁻⁴。

旧配对升级：不强制失效，记录标 `pairingProtocol = 1`。升级方式只有一种——用一个新的 v2 码重新配对；不提供经旧通道原地换密钥（旧配对当时若已被中间人插入，带内换钥继承的是同一个中间人）。重新配对清不掉中间人在 v1 时留下的记录（那条记录在攻击者的指纹下）：升级后请解绑不认识的设备。

## 6. 落盘、回滚与已知局限

`PairingStore.commit`：地址簿 → 索引 → `vault.set`，vault 写入是唯一的提交点；任一步失败按相反顺序恢复。暂存的提交在 `activate()` 之前不生效。回滚先读当前值，只有它仍是本次写入时才写回旧值或删除；目标是「没有记录」时一律先在进程内吊销该指纹再删。吊销只由新的生效写入解除。

已知局限与残余：

1. **提交时读旧值失败。** Windows 凭据库的读取会吞掉错误：提交那一刻读失败，旧值被当成「没有」，而新值已经覆盖旧记录。这次握手若失败，回滚走删除分支，原有的配对没了，需要重新配对。不产生权限残留。
2. **暂存期间的地址簿。** 地址簿不在生效视图里，暂存期间它已经是新地址；回滚或生效之后恢复正常。
3. **M4 丢失（两将军问题）。** H 已落盘而 `done` 丢失：J 回滚，H 留下一条没有任何人持有密钥的记录（设备列表里多一台永远离线的设备，需手动解绑）。重新配对场景下 H 换成了新密钥、J 恢复成旧密钥，两边连不上，要再配一次。在途攻击者可以故意制造这个状态，也可以伪造 `done` 让 J 留下悬空记录，两者都只是拒绝服务。
4. **凭据库吞错。** 删除之后的确认性读取若因故障返回「没有」，会把没删掉的条目报成干净；本进程内不受影响（已吊销），重启后设备页会出现一台设备，它的密钥只有那次握手的对端算出过。
5. **崩溃边界。** 暂存只是进程内的状态。J 在「已落盘、未收到 `done`」之间进程退出，记录保留在 vault 里，重启后是一条生效的记录；H 没落盘的话它是一条不可用的悬空记录。不做启动期自动清理（分不清它和有效配对）。
6. 重新配对失败会让原有连接断开重连一次（回滚后一律关掉该指纹的连接再用生效的密钥重拨）。
7. **只在一侧解绑之后用 8 位旧码重配。** 解绑只删本机的记录，不通知对端，所以两端可能一侧留着 v2 记录、另一侧没有。
   - J 留着 H 的 v2 记录、H 已解绑 J：J 的预检按地址簿认出目标地址名下有 v2 记录，本地拒绝（`PAIR_LEGACY_DISABLED`），不发任何请求；在 J 上解绑后即可重配。预检只认地址——H 换了地址，或这次填的主机写法与地址簿里记的不同，它就认不出来。这时 H 先落盘并消费了配对码，J 随后才在落盘前被「v1 不得覆盖 v2 记录」拒绝：H 的设备页多出一台永远连不上的设备（那条 v1 记录的密钥 J 没有存），J 报失败并保留原来的 v2 记录。恢复办法是两侧都解绑后重配。不产生第三方权限。
   - H 留着 J 的 v2 记录、J 已解绑 H：H 拒绝，J 的界面提示「对方不接受旧的 8 位配对……得先在对方的设备页解绑这台设备」。H 的界面没有提示，那个 8 位码继续有效到过期。
8. **H 重建出站只看两个信号**：替换了旧记录，或断之前出站在线。提交那一刻凭据库读旧值失败（第 1 条）而 H 的出站又恰好在断线重试的间隙里，两个信号都是假，H 的出站循环被摘掉后不重建。J 的出站照常重拨，连接不受影响；只是此后 J 重启的话，要等 H 重启才连得回来（H 是拨号方的设备对）。
