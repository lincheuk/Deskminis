# F03 同模型超窗恢复与可验证压缩

状态：已实现（验证全部在假端点上完成，没有调过真实模型）。依赖 F02 的请求预算（`RequestBudget` / `LimitProfile`）。

## 1. 解决什么

- 端点以「上下文超出」拒绝请求时，以前直接换窗口更大的模型，没有就报「上下文已满」。现在先在同一个模型上恢复。
- 压缩摘要以前是一段自由文本，没有版本、覆盖区间与校验。现在是带结构的标记，写入前校验，并附一段由程序生成、模型改不了的记录。

以前就有、原样保留的保证：摘要提示覆盖目标与约束、进展、关键决策、文件路径、待办；原历史永不改写；最近 3 个用户回合保留原文
（单回合长任务保留最近 14 条）；空、截断、被拒的摘要不落库；取材后退时不拆工具调用与结果。

## 2. 有界恢复序列

```
端点回超窗
  → 固定开销（系统提示 + 工具定义）自己就占满资料上限？是 → 不恢复
  → 记下拒绝上限，进预算（computeSlotBudget 的 ceiling）
  → 回到轮首，带着上限重走同一条请求构建路径：
      收输出（上限进了预算，max_tokens 由同一条公式收紧）
      → 修剪第 1、2 级（余量不足就做）
      → 标准锚点的压缩（余量不足且值得、摘完放得下才发）
      → 第 3 级裁剪最近的大结果（放不下才做）
      → 收紧锚点的压缩，只留最近 4 条（放不下才做）
  → 预算不再是 over → 同槽重发（每次事故最多 2 次）
  → 否则：窗口更大的槽位 → requestBudget / contextFull
```

顺序的理由：收输出与修剪旧结果不花钱，丢的是模型已经用过的内容；标准压缩花钱，但保住最近的工具轨迹与最近 3 个用户回合；
裁剪最近的大结果不花钱，但动的是模型刚拿到的内容；收紧锚点的压缩是最后一档。每一档之后用同一把尺（带上限的预算）重判，够了就停。

恢复只修请求构建。端点拒绝之后到下一次成功的流之间，不追加消息，不调调度器、运行记录器、权限网关；已执行的工具不重跑。

被拒绝过的槽位在之后每一轮的轮首：F02 的三步之后预算仍放不下时，先做阶梯的后半段（第 2 级修剪、第 3 级裁剪、收紧锚点的压缩）再发请求，
不发主请求、不计重发与拒绝次数。故障降级到的槽位需要先减压时，回轮首按它的窗口重走（以前照发）。
本轮按输出额度换过槽的（F02 后续修正），整轮不做同槽恢复。

### 2.1 拒绝上限（`RejectionCeiling`）

run 级、按槽位、只降不升，不跨运行保留。定法依次是：

1. 报文带可用的数字（`overflowHint`）：按「端点数的 ÷ 本机估的」换算成本机口径后留 5%；比例出了 [0.5, 3] 的不用；
2. 先收输出：共享窗口、第一次被拒、申请的输出明显大于 16,384——只记「输入 + 输出放不下」，输出上限钉在 16,384；
3. 其余：按被拒输入的 25% 下调（至少 1,024）。

收口：比被拒那次至少小 1,024。读的一侧（`applyCeiling`）先按当前校准系数换算；同一配置实例成功收下过的输入是下限；
资料上限可信时与它取小，不可信（窗口没有资料、已被实测推翻）时只用学到的值。`authority` 恒为 `advisory`：只用来判水位、收紧输出、判 over，永不据此拒发。

### 2.2 熔断（`RECOVERY_LIMITS`，在 `src/shared/compaction.ts`）

| 熔断 | 上限 |
|---|---|
| 同槽重发 | 每次事故 2 次 |
| 处理的超窗拒绝 | 每次运行 6 次，再多一次直接放弃同槽 |
| 成功的压缩 | 每次运行 3 次（水位压缩与恢复共用）；失败一次本次运行停用 |
| 摘要请求 | 每次运行 5 个；每次 `summarize` 2 个（第 2 个只在摘要请求自身超窗时发，取材减半） |
| 摘要花费 | 累计「取材的本机估算 + max_tokens」40 万。取材量不乘校准系数，与「一次摘要最多取 10 万」是同一口径：3 次满额摘要约 35 万，不收紧上面的 3 次 |
| 无进展 | 预算仍是 over 不重发；摘完之后的下限仍放不下不发摘要请求 |

这几个数没有对着真实端点调过。`RunOptions.recoveryLimits` 可以收紧。

停在压缩次数、摘要请求次数、摘要花费，或压缩此前失败过已停用时，这次事故的恢复说明一定发（`error.recovery` 的动作里是
`skipped(limit / requests / spendCap / disabled)`）：那以此前压缩过或试过为前提，用户看到的不能只是一句「上下文已满」。
没有可摘的、摘走的太少、摘完仍放不下（这次确实没有可减的）且没有别的动作时保持静默。

## 3. 结构化压缩标记（`CompactMeta` v2）

存在设备本地的 `compact_marker_meta` 表（一条 marker 至多一行，与 marker 行同一个事务写入）。`compact_markers` 的列不变，
同步线路不变；没有 meta 行的 marker 就是旧 marker，读的一方按没有 meta 处理。

- `coverage`：从会话第一条到锚点、这一次新摘进来的那一段、上一条 marker、锚点规则（`recent-turns` / `recent-messages` / `tight`）。
- `model`：模型写的七个小节（目标、约束、已完成、进行中、待办、关键决策、涉及文件），加上一份摘要里有、这次没复述的约束。
- `evidence`：程序根据落库消息生成——用户指示原话（第一条加最近 5 条）、工具成功写入的文件、其它有副作用的调用及其结果、未落定的调用数。
- `record`：因何触发、哪个槽位、触发时的预算、摘要请求的大小与次数。
- `summaryDigest`：`marker.summary` 的指纹；summary 或锚点被同步合并改写过时 meta 作废。

`marker.summary` 只放模型那一半（结构化时是核对之后渲染的分节文本）。程序记录在发请求时从 meta 渲染，接在摘要消息里。

### 3.1 写入前的检查（任一不过都不写）

截断 → 被拒绝 → 为空 → 格式（出现了小节标题而结构不完整 = `malformed`）→ 结构与历史是否一致（`invalid`）→ 已取消 →
最新 marker 变了或历史前缀变了（`stale`）。失败后本次运行停用压缩，上一条有效 marker 原样保留。

陈述核对（`checkClaims`，确定性、不调模型）：【已完成】里的路径没有佐证的整条移除；【进行中】里的挪到【待办】；
「测试通过」这类验证结论，覆盖区间内没有任何成功的有副作用调用时移除，有则注明程序没有核对；【涉及文件】里对话中没出现过的路径移除。

【已完成】【进行中】的一条里，路径有没有佐证分三档判（证据是覆盖区间内工具调用的入参；「出现过」= 任何一次调用，「动过」= 成功的写入与其它有副作用的调用）：

- 有路径哪一次调用的入参里都没有（工具从没碰过）→ 没有佐证。
- 路径都出现过，其中至少一个动过 → 有佐证。「参照 A 的写法，在 B 里新增了…」（A 只读过、B 改过）因此留下。
- 路径都只是读过的（或写入失败、已取消、结果未知）→ 条目带修改类字眼（修改、写入、新增、创建、删除、重写、更新…，英文 edit / wrote / creat… / modif… / updat… / delet… 等）
  才算没有佐证：「已修改 X」移除，「已阅读 X，定位到根因…」「检查了 X，确认…」留下。只读的排查、审查会话，结论全在这样的条目里。

【涉及文件】认全部调用的入参与用户消息（那一节只要求路径出现过）。路径样记号切分前，反引号与引号换成空格（中文行文里路径两侧常常只有反引号、没有空格）。

它是启发式的，两个方向都有漏：

- 漏放：裸文件名不核对；路径只要在任何一次成功的有副作用调用的入参里出现过就算动过（shell 命令串里提到即可）；
  一条里既有动过的路径又有只读过的路径时整条留下，分不清修改类字眼说的是哪一个（「已修改 A 和 B」、A 只读过）——确实被工具改过哪些文件，以程序记录的文件变更为准；
  只读过的路径上用词表之外的说法声称改过（「已拆成两段」）认不出；
  验证结论只要覆盖区间内有任意一次成功的有副作用调用就保留并加注——程序分不清哪条命令是在验证；换个说法的验证结论认不出。
- 误删：只读过的路径上，如实的条目里出现了修改类字眼（「检查了 X，无需修改」「定位到根因：写入前没有加锁」）；只出现在工具输出里的路径；
  没有引号、中文直接贴着路径写的（「已写入out/a.md」）；英文行文里的斜杠列举（`client/server/db`）会被当成路径。
  日期（`2026/10/04`）、分数与中文行文里的斜杠列举（「增/删/改」）不算路径。

工具调用的 id 不保证唯一（有的端点按响应内序号发 id，有的不给）：取证与校验都按「紧邻的下一条消息、同一批里按出现次序」配结果，
文件变更按声明它的那条消息定位，不在整段历史里按 id 取第一条。请求侧裁剪的说明句同理，只看紧邻的前一条 assistant 声明的调用。

### 3.2 自由文本摘要（待审核人裁决）

没有任何小节标题的回复只在以前就有的路径上照收（水位或余量触发、标准锚点、上一条 marker 不是结构化的），记为 `form: 'text'`。
端点拒绝之后的压缩、收紧锚点的压缩、上一条是结构化 marker 时不收（按 `malformed` 失败）。两个方向都只动 `summarize` 里那一处判断。

### 3.3 锚点与保留回合

- 规则锚点不拆工具对（落在 toolUse 上、下一条是它的结果时退一条）。
- 数最近 3 个回合仍只数带文字的用户消息（改数纯图片消息会让锚点变晚）。
- 被摘要盖住的保留回合（最近 3 个带文字的用户回合，并上最近 3 个含纯图片的用户回合）读的时候按原话全文接在摘要消息后面，
  最新一条的图片也带上。这一段按传入的历史现算，不读 meta，所以旧 marker、同步来的 marker 同样有。

## 4. 事件、审计与界面

- 事件：`contextRecovery`（一次事故的全量状态：被拒的请求、每个动作、重发的请求、停在哪条熔断）；`compacted` 带 `detail`；
  `pruned` 的第 2、3 级带 `level` 与 `clipped`；`compactFailed` 带 `trigger`；`error` 可带 `recovery`。
- 审计：`context.compacted`（覆盖、计数、前后预算，不带摘要正文）、`context.compactFailed`、`context.recovery`
  （重发没有完成的那一条带 `interrupted: true`）。
- `chat.contextInfo` 多两个可选键：`compaction`（来自库）与 `recovery`（仅内存，下一次 `chat.prompt` 时清）。
- 界面：事件条一条「上下文超出模型上限：…后重发 / 已在同一模型上恢复 / 同一模型上放不下，改用 X / 同一模型上恢复不了」
  （停在本次运行的熔断上时写明是哪一条，如「同一模型上恢复不了：本次运行的压缩次数已用完」）；
  任务面板的「上下文恢复」卡与「上下文已压缩」卡的覆盖、保留项两行。压缩卡在本次运行刚压缩过、或这个会话的库里有压缩记录时显示
  （重开会话、重启之后靠 `chat.contextInfo` 带回的摘录；这份摘录是会话级的，发新消息时不清，只在换会话、删除会话时清）。`chat.contextInfo` 的应答晚到（请求在途时换了会话或发了新消息）时整条丢弃。

## 5. 没有做、已知的边界

- 没有真实端点证据：摘要协议的遵从率、真实的超窗报文与数字口径、流中途到达的超窗，都只有假端点用例。
- assistant 消息里工具调用的大入参不裁剪，只能靠压缩。
- 经 shell 做的文件改动不在「文件变更」里（列在有副作用的调用里）。
- meta 不上同步线路：对端与旧版本没有程序记录；旧版本收到收紧锚点的 marker 时，最近的用户指示只有摘要转述。
- 拒绝上限随校准系数的换算对带很多图片的请求有偏差。

## 2026-10-05 整合增补（F11B、F08、F06）

- 陈述核对先排除路径和代码标识符的拼写，再在剩余谓语里识别修改类字眼。带修改词干的文件名、camelCase / snake_case、点分名、连字符标签与反引号中的简单标识符不再导致只读结论被移除；普通的 Updated / modified 或“已修改”仍须有副作用记录佐证。这仍是词法启发式，不是语义证明。
- compact_marker_meta 顺延为 MIGRATIONS[15]，user_version=16。此前 [0..14] 的 SQL 与钉值不变；按会话的物理清理集中在 purgeSessionRows。对端删除后保留副本仍保存元数据，显式恢复可读；覆盖、释放和彻底删除会清掉元数据。
- F03 的内存恢复状态随统一生命周期钩子清除，包含对端墓碑和保留副本；chat.contextInfo 不向删除态会话返回新压缩记录视图。恢复持久历史不会复活旧运行的恢复状态。
