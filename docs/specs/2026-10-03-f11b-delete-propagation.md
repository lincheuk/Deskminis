# F11B 删除同步与跨设备冲突

删除会话会同步到已配对的设备，旧副本带不回来；恢复只能显式做出。本文是实现之后的规格：数据、线格式、规则、收敛、边界与未验证项。
代码在 `deskminis/src/minisd/sync/`（`wire.ts`、`lifecycle.ts`、`receive.ts`、`rpc.ts`、`coordinator.ts`）、
`deskminis/src/minisd/store/chat-store.ts` 与 `deskminis/src/minisd/index.ts` 的同步装配段。

本文取代 `2026-07-26-deskminis-design.md` 里设想的 `deleted_record_tombstones`（30 天 TTL）：那个 TTL 到期之后，
长期离线的设备带着旧副本回来就能把会话复活，本文的删除记录不过期。

## 1. 模型

- **每个会话至多一条登记** `(v, opId, originDeviceId, at, seen?)`，存在表 `session_lifecycle` 里（迁移 `[13]`，跑完后 `user_version` 为 14）。
  `v` 是整数版本：奇数 = 已删除（这条登记叫墓碑），偶数（≥2）= 删除后被显式恢复；没有登记等于 `v = 0`，从未删除。
  `opId` 是造成这个版本的那次动作的随机 id。`originDeviceId` 是做这次动作的设备指纹。
- **全序**：先比 `v`（大者胜），`v` 相同比 `opId`（字典序小者胜）。每台设备对每个会话保留全序最大的那一条。
  删除与恢复各把 `v` 加一。**任何裁决都不读时钟**：`at` 是发起端墙钟，只给人看和进审计；两台设备的时钟差几天不影响结果。
- **seen**：删除方在删除那一刻持有的全部消息 id（升序、去重），外加条数与摘要
  （`sha256(ids 以 '\n' 连接)`）。接收端用它判断自己手里有没有删除方没见过的内容。超过 20000 条时不带 id 列表。
- **一个会话在一台设备上只有三种状态**：

  | 状态 | 登记 | `sessions` 行 | 内容 | 在会话列表里 | 参与同步 |
  |---|---|---|---|---|---|
  | 存活 | 无，或偶数 | 有，`remote_tombstoned_at` 为空 | 有 | 是 | 是 |
  | 已删除（已清） | 奇数 | 无 | 无 | 否 | 只传墓碑 |
  | 已删除（保留副本） | 奇数 | 有，`remote_tombstoned_at` 非空 | 有，冻结 | 否（在设备页「已在其他设备删除」里） | 只传墓碑 |

- **预留列的取舍**：`sessions.remote_tombstoned_at`（迁移 `[0]` 预留）用作保留副本的隐藏标记，值是本机应用墓碑的时刻，只用于展示；
  它不是墓碑本体——挂在会话行上的标记随行一起消失，拦不住旧副本，一个时间戳也装不下版本、动作 id 与 seen。
  `remote_origin_device_id`、`last_synced_at` 不用。
- **不变量**：会话行只在同一事务里登记已是奇数时才物理删除（`purgeSessionRows` 是全仓唯一的删除点，开头有运行期检查）；
  登记只增不减；登记为奇数时这个会话什么都写不进去——消息与摘要（`appendMessage`、`appendCompactMarker`）、
  会话属性（标题、工作区、模型绑定、助手、记忆开关、MCP 禁用名单）、标注的增改删，在存储层一律抛「会话已删除」，合并入口整包拒收；
  会话的技能覆盖不归会话存储层写，`skills.setEnabled` 带 `sessionId` 时在处理器里同样抛「会话已删除」；
  `sync.ack` 对它是空操作（不改会话行的 `last_synced_at`，应答与对不存在的会话相同，不报错）；
  登记为偶数则会话行存在；`session_lifecycle` 的行永不删除。
  保留副本因此是冻结的：它被留下的依据（对方没见过的消息、本机标注）在用户恢复或彻底删除之前不会变。
  冻结的范围是会话的内容与属性：消息、摘要、会话行、标注、技能覆盖。不在其内、也不是对会话的写入的：
  卸载一个技能时它在各会话里的覆盖行一并删掉（保留副本也不例外）；运行账本、附件索引与文件检查点各有自己的口径（§3.10、§3.9、§3.11）；审计独立于会话。

## 2. 线格式

在既有的 `sync.push`、`sync.pull`、`sync.list` 上加可选字段，方法名单不变，协议版本号不变。能力位 `tombstones`（`SYNC_CAP.TOMBSTONES`）
在 `sync.hello` 里声明；对端不声明就不向它发墓碑。

```ts
interface WireSeen { count: number; digest: string; ids?: string[] }
interface WireLifecycle { v: number; opId: string; originDeviceId: string; at: number; seen?: WireSeen }
interface SyncPayload { messages: WireMessage[]; markers: WireCompactMarker[]; session?: WireSession; lifecycle?: WireLifecycle }
```

- **墓碑载荷** = `{ messages: [], markers: [], lifecycle }`，`lifecycle.v` 为奇数。接收端不看其中的消息与摘要。
- **恢复过的会话**（登记为偶数且 ≥2）的每一个载荷都带 `lifecycle` 与 `session`（分批推送的每一批都带）。
- `sync.push` 的应答多出：`rejected`（`'tombstoned'` = 接收端已删除且版本更高；`'session-required'` = 载荷带更高的偶数登记，
  但接收端没有会话行、载荷里也没有 `session`）、`tombstone`（墓碑载荷的结果：`applied` / `superseded` / `duplicate` / `stale` / `deferred`）、
  `restored`、`sessionCreated`、`lifecycle`（接收端操作之后的登记，供发送端追平）。
- `sync.pull` 一个已删除的会话：认识墓碑的调用方拿到墓碑载荷；其余照旧报「会话不存在」。
- `sync.list`：`sessions[]` 里恢复过的会话带 `lifecycle: { v, opId }`；认识墓碑的调用方多一个 `tombstones: [{ id, v, opId }]`；
  应答端暂停时不给清单，只带 `lifecyclePaused: true`。
- **解析**：网络输入按 unknown 处理，绝不抛错。`v` 须为 1..1000000 的整数，`opId` 匹配 `/^[A-Za-z0-9-]{1,64}$/`，
  `originDeviceId` 匹配 `/^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$/`，`at` 为有限数——任何一项不合规，整个 `lifecycle` 当作没有
  （垃圾输入不会被当成墓碑，也不会被当成恢复）。`seen` 不合规整个丢弃，`ids` 与 `count` 对不上只丢 `ids`：丢弃的方向都是让接收端保留而不是清除。

## 3. 规则

### 3.1 本机删除

一个事务：版本加一写墓碑（`seen` = 此刻的全部消息 id）→ 清这个会话的内容行（消息、摘要、孤儿摘要、标注、技能覆盖、附件索引行、运行账本行、文件检查点记录、会话行）。
任何一句失败都整体回滚。这个 id 名下什么都没有时不写墓碑（重复删除幂等；只剩技能覆盖行或运行账本行的 id 也算这一种，这些行清掉、不造墓碑）。
对保留副本调用时只清内容、版本不变。
运行中的会话先停下再删（既有行为）；停不下来就不删并报错，此时既没清内容也没写墓碑。

界面上保留副本的「彻底删除」不走这个方法，走 `chat.sessions.purgeRetained`（`ChatStore.purgeRetained`）：同一个事务里先确认
它此刻仍是保留副本（会话行在、隐藏标记非空、登记为奇数），是才清内容，版本不变、不再同步；不是就报错，什么都不动。
分开的原因：`chat.sessions.delete` 分不出调用方的意图。保留副本刚被另一台设备（或本机另一个窗口）恢复、设备页上的清单还没重拉时，
同一个调用落到的是一个存活的会话，会写出新的墓碑、把刚恢复的会话在所有设备上再删一次。

### 3.2 收到墓碑

先让本机这个会话停下（权限卡按 `session-deleted` 了结、中止 run、等收尾），释放终端与 shell，再在一个事务里重新判定并落库——与本机删除同序。
run 在 10 秒内停不下来：推迟，run 自己收尾后本机重试；对端下次对账也会重送。落库之前（入口、等 run 停下之后、延后重试的入口）
复查三件事：进程没有在关停、本端没有暂停、送来这条墓碑的设备仍在配对表里；任何一条不成立就不落库。

| 对端墓碑与本机登记相比 | 登记 | 内容 |
|---|---|---|
| 全序更大（对端胜出） | 换成对端的 | 没有会话行：清残留行。有会话行：对端的 seen 覆盖本机全部消息**且**本机没有标注 → 清除；否则隐藏并保留，内容一行不动 |
| 同一条，或同一代输在 `opId` 上 | 不动 | 本机是保留副本时用这条的 seen 再判一次，覆盖了就清除 |
| 更早的一代 | 不动 | 不动 |

保留副本被清除，当且仅当本机实际收到过的本代或更新一代的某一条墓碑的 seen 覆盖了本机全部消息，且本机没有标注。
墓碑没有 id 列表（已压实或超过上限）时，只有本机消息集合与删除方当时的完全相同（条数相等、摘要相等）才算覆盖。
重复、过期的墓碑不写库、不转发、不广播、不记审计。

### 3.3 收到内容（防复活闸）

合并事务的第一步，在任何写入之前：

| 对端载荷的登记与本机相比 | 本机登记 | 结果 |
|---|---|---|
| 更低，或不带登记 | 奇数（已删除） | 整包拒收（`rejected: 'tombstoned'`），一行不写。分批推送里只带消息的批次同样在这里被拒 |
| 更高的偶数 | 奇数 | 接受（显式恢复）：登记换成对端的，保留副本原地解冻，然后合并 |
| 更高的偶数 | 偶数或无 | 登记换成对端的，然后合并 |
| 不更高 | 偶数或无 | 照常按 id 并集合并，登记不动 |

采纳偶数登记要求事务结束时会话行存在（本机已有，或载荷带来）；否则 `rejected: 'session-required'`，登记不动。
认识墓碑的对端拿到 `rejected` 加本机登记，当场对自己的副本应用这条墓碑；不认识的对端收到的是错误 `sync.push 被拒：会话已删除`。

闸判的是载荷外层的会话 id，而每条消息、每条摘要在线格式里还各带一个 `sessionId`。两者不一致的条目在合并之前丢弃（记一条警告），
不落库、也不改绑到外层的会话：否则对端可以借一个存活的会话，把内容写进本机已删除的另一个会话。守约的发送方不会发出这种条目。

### 3.4 冲突政策

| 并发操作 | 结果 |
|---|---|
| A 删除，B 没有新内容 | 两端都删除，内容都清掉 |
| A 删除，B 离线追加了消息 | 两端都不再存活。A 清掉，不会收到 B 的追加。B 的会话从列表消失、内容原样保留并提示；B 可以恢复（新版本，传回 A，含追加的消息）或彻底删除 |
| A 删除，B 离线改了标题、记忆开关、模型绑定、置顶，或做了压缩 | 删除生效，B 的副本清掉；属性修改随会话一起消失 |
| A 删除，B 上这个会话有本机标注 | B 保留副本并提示有 N 条本机标注（标注不同步，删除方不可能见过） |
| A、B 各自删除 | 版本相同，登记取 `opId` 小的那条；两端都已清 |
| A 删除，B 上该会话有 run 在跑 | run 被中止；中止收尾时写下的消息 A 没见过，B 保留 |
| 墓碑与恢复乱序、重复到达 | 登记取全序最大值，与顺序和重复次数无关 |

### 3.5 显式恢复

只能由持有保留副本的设备做出（设备页「恢复」，`chat.sessions.restore`）：登记写成 `v + 1`（偶数）、新的 `opId`，隐藏标记清掉，然后照常同步。
恢复与「旧副本被同步回来」的区别只在版本，不在时间。恢复回来的内容是恢复时各设备仍持有的内容的并集；已经清掉且没有任何设备留着的内容不会回来。
两端各记一条审计（`session.restored`、`session.restored.remote`）；登记行本身记着做恢复的设备与动作 id。

### 3.6 对账

拨号方每次上线：取对端的 `sync.list`（含墓碑头清单）→ 先拉对端有而本机没有（或更旧）的墓碑 → 推本机的存活会话，再把对端缺的墓碑逐条推过去
→ 拉对端的存活会话（本机已删且对方手里是旧副本的不拉）。对账是无状态的：不记「谁确认过哪条墓碑」，每次比头清单、只补差量；
两端墓碑一致时墓碑不产生额外 RPC。墓碑会转发给所有声明了能力的对端，不管对方有没有过这个会话——第三台设备带着旧副本接进来时，任何一台都挡得住。

### 3.7 暂停、取消配对

- **暂停**：墓碑平面双向静默——本端的删除不发出，对端的删除不应用；防复活闸照常（旧内容照样被拒）；内容平面沿用既有行为（对端内容照收）。
  恢复同步后补齐：暂停期间本机做的删除补发，对端做的删除在下一次推送或拉取时拿到。
- **取消配对**：只断连接、删配对记录。期间两边的删除互不到达；那台设备尚未落地的删除（正等本机的 run 停下）不再应用。
- **重新配对或第一次配对**：首次连接即全量对账，按登记补传。本机删过的会话（包括没有任何已配对设备时删的、取消配对期间删的），
  对方设备上如果还有，会被删除；对方有本机没见过的内容时走「保留」。删除不按设备划范围：让闸对某些设备放行，就是让旧副本能回来。

### 3.8 墓碑 GC

墓碑行不自动删除：整行删掉之后，带着旧副本回来的设备与一个全新的会话在协议上分不出来，而「全部已配对设备都确认过」不是安全条件
（取消配对后重新配对、只与其中一台同步过的第三台设备、从备份还原的数据目录都会带着旧副本回来）。
GC 是**压实**：本机记录满 90 天的墓碑把消息 id 列表置空，条数与摘要留着；保留副本的那一行不压。启动时做一次。

| | 压实前 | 压实后 |
|---|---|---|
| 带着旧副本回来的设备（副本是删除方见过的子集） | 被拒收并收到完整墓碑，清除 | 副本与删除方当时的完全相同则清除，否则保留待用户决定 |
| 带着有新内容的副本回来的设备 | 保留，界面给出准确条数 | 保留，界面写「无法确认」 |
| 删除方能否被复活 | 不能 | 不能：闸读的是 `(v, opId)`，压实不动它 |

代价：每个删过的会话一行，压实后约 200 字节，压实前另加每条消息约 39 字节；`sync.list` 每次对账带全部墓碑头（每条约 100 字节）。

### 3.9 附件（F11A）

已删除的会话（含保留副本）对附件同步等同没有任何引用：不登记、不列进清单、不送出、不受理，`attachments.retry / cancel` 被拒。
在途的取回在下一块之前停下。清库时附件索引表的行随会话一起清；**附件文件与 `sessions\<id>\` 目录不删**。
保留副本的附件行与文件原样留着，恢复之后重新参与同步。

### 3.10 运行账本与启动恢复（F05）

`agent_runs`、`tool_executions` 按会话归属、只在本机、不进同步。

- **清除**：会话被物理清掉时（本机删除、对端墓碑覆盖全部内容、彻底删除保留副本），它的账本行在同一个事务里清掉。
- **保留副本**：账本行与内容一起原样留着。显式恢复之后「第几次运行」接着数，旧的 `promptId` 仍然去重。
  接受恢复的另一端当初清掉了账本行，从第 1 次数起。
- **落库时没有在跑的 run**：本机删除与对端墓碑都先等 run 收尾。收尾（补送没交付的工具结果、落 run 的终态）做完之后才写墓碑，
  之后没有任何路径再往这个会话写消息或账本行。对端删除打断的 run 记 `cancelled` / `session-deleted`，定时任务的终态记「会话已删除」。
- **已删除的会话拒写、不显示**：`chat.prompt` 在入口拒绝（「会话已删除」），排在 `promptId` 幂等检查与占用 run 之前——
  不起 run、不留 run 行；保留副本上重发同一个 `promptId` 得到的也是这一句，不是 `duplicate`。
  `chat.runs.snapshot` 不带出已删除会话（含保留副本）的运行与工具执行。定时任务每次触发新建会话，不会打到已删除的会话上。
- **启动恢复**：生命周期自检排在启动恢复之前。恢复只给「会话行可见」的会话补结果消息：保留副本、已清除却还留着账本行的会话，
  那一批只关账（记已交付、不补消息），run 记为中断；不抛，不挡启动。保留副本恢复之后，那次没有结果的调用由请求侧补占位。

### 3.11 文件检查点（F08）

`file_checkpoints`、`checkpoint_blobs` 与数据目录 `checkpoints\` 下的内容文件按会话归属、只在本机、不进同步。
内置的文件写入、文件编辑、Office 文档生成每改一个文件留一条记录，写入前的内容存成内容文件；用户可以在「改动」页把文件恢复到改动之前。

- **清除**：会话被物理清掉时（本机删除、对端墓碑覆盖全部内容、保留副本被释放或彻底删除），它的检查点记录在同一个事务里清掉
  （`purgeSessionRows`），不再被任何记录引用的内容文件随即回收（生命周期钩子里做，不等下一次写入、看「改动」页或重启）。
  此后这个会话做过的改动不能再经检查点恢复；用户的文件本身不动。
- **清除不连累别的会话**：同一个文件上别的会话的记录留着。它们此后按文件现在的内容判：字节仍是那次改动写入的
  （被清除的会话恢复过自己的改动，或把内容改回去过）就照常能恢复；被清除的会话的改动还留在文件里的，判为「被修改过」，只能另存改动前的版本。
  为此清除时在同一个事务里把这些路径上别的会话记录里的文件 ID 置空：文件 ID 是沿同一路径上的全部记录推出来的
  （本应用每次写入、每次恢复都会换掉它），少了被清除会话的那几条就推不出来，留着旧值会把一个字节没变的文件判成
  「换成了另一份内容相同的文件」。置空之后这几条记录恢复时不再比文件 ID，内容哈希、大小、硬链接数与动手前的复核不变；
  代价是「被另一份内容相同的文件替换」在这几条记录上认不出来（内容相同，恢复不丢东西）。
- **占位行**：还记着残留临时文件的记录（用户目录里一时删不掉的 `.dm-*.tmp`）不直接删，留成不带内容引用的占位
  （`aborted` / `session-deleted`），检查点存储确认临时文件已不在之后删掉它。这是「已清除的会话名下没有内容行」在这张表上的例外：
  占位行不含任何文件内容、不出现在清单里；重复删除（这个 id 名下已没有会话行与消息）不动它。
- **对端删除落地**：与本机删除相同——这台设备上由这个会话改过的文件，此后不能在「改动」页恢复（「已配对的设备等同本机」，见 §5「权限」）。
  本机有删除方没见过的消息或标注时走保留，检查点随副本留着。
- **保留副本**：检查点记录与内容一起原样留着，冻结——运行期间不对它对账、不恢复、不另存；启动时的全局对账除外（见下「启动」）。按保留期（30 天）与容量的清理是全局的，
  对它的记录一视同仁（到期或被挤掉时标成已清理、回收内容）；这不是对会话的写入，会话行与消息不动。占用统计照算。
  别的会话被清除时，保留副本在同一个文件上的记录里的文件 ID 同样置空（见上「清除不连累别的会话」，那一句不区分保留副本）：
  记录的状态与内容引用不动，会话行与消息不动；显式恢复之后这些记录照常能恢复。
- **已删除的会话不显示、不恢复**（含保留副本）：`checkpoints.list` 返回空清单（不报错，占用照给）；
  `checkpoints.inspect` / `diff` / `restore` / `saveCopy` 报「会话已删除」，文件与记录不动。恢复在等文件锁期间会话被对端删除、落成保留副本的，
  拿到锁之后重判为不可恢复（`session-deleted`）。`checkpoints.usage` / `setQuota` 是全局的，不受影响。
- **显式恢复之后**：检查点照常可用（清单、对比、恢复、另存）。接受恢复的另一端当初清掉了记录，
  那些改动在它那里列在「没有检查点的改动」里，只能查看当前文件。
- **别的会话的记录被保留副本挡住**：同一个文件之后被一个保留副本改过时，本会话的记录是「之后还有改动」。
  审阅面板对不在会话列表里的会话不给跳转，写明先在「设备」页恢复它；彻底删除那个副本之后，本会话的记录按文件现在的内容判（见上「清除不连累别的会话」）：
  副本的改动还留在文件里，就是「被修改过」，只能另存改动前的版本。
- **启动**：生命周期自检 → 检查点对账 → 启动恢复。对账是全局的，只落定检查点自己的记录（含保留副本的）与库里记着的临时文件，
  不改用户文件、不往会话里写；启动恢复对保留副本只关账（§3.10），检查点给出的文件事实因此用不上。

## 4. 收敛

- 登记是全序 `(v, opId)` 上的取最大值：幂等、可交换、可结合。收到同一组动作的设备登记相同，与重复次数、到达顺序、经过几台设备转发无关。
- 存活与否只由登记的奇偶决定，各设备对「这个会话还在不在」的答案相同。存活时内容按 id 并集合并，收敛性不变。
- 删除态下没有共享内容。保留副本是设备本地的私有状态，不参与同步。**收敛的结论到登记、存活集合、存活会话的内容为止，不包括保留副本**（见边界表）。
- 终止性：重复与过期的墓碑不引起再同步；被拒的内容不引起再同步；登记相等的合并沿用原有的「有变化才再同步」。

## 5. 边界

| 情形 | 行为 |
|---|---|
| 旧版对端（不声明 `tombstones`） | 收不到删除，留着自己的副本；它推已删会话被拒（报错），拉已删会话得到「会话不存在」；它自己删掉的会话（物理删、无墓碑）会被新版推回去；经旧版中继的第三台新版设备要直接配对到持有墓碑的设备才删除。其它会话的消息同步照常 |
| 暂停 | 暂停期间删除既不发出也不生效，内容照收；恢复后补齐 |
| 升级前的删除 | 没有墓碑，仍可能从持有副本的设备回来一次；回来后再删一次即留下墓碑 |
| 没有已配对设备时的删除 | 照样写墓碑。以后配对的设备上如果还有这个会话，会被删除（对方有本机没见过的内容时保留） |
| 取消配对期间的删除 | 期间不传。重新配对后按登记补传，对方上的这些会话同样被删除 |
| 并发删除时的第三台设备 | 两台设备各自删除同一个会话、seen 不同，落败的那条墓碑在发起端被赢家覆盖后不再传播。第三台设备的消息只被落败那条覆盖时：赶在覆盖之前收到过它就清除，否则保留待用户决定。三台设备的登记与存活集合不受影响，差别只在多留一份副本 |
| 对端删除时本机会话正在跑 | run 被中止，本机保留副本。最长推迟 10 秒；停不下来时推迟到 run 结束 |
| 等 run 停下期间来源设备被取消配对 | 墓碑丢弃，会话仍存活；已经发出的中止不撤回，那个 run 按已取消收尾 |
| 恢复 | 找不回已经清掉且没有任何设备留着的内容 |
| 恢复推到一半断线 | 接收端是一个内容不全但可见、照常同步的会话，之后的对账补齐 |
| 会话属性（标题等） | 仍按 `updatedAt` 后写胜出，与删除无关 |
| 登记到上限 | 版本上限是 1000000（删除与恢复各加一）。到上限的会话本机删除报错、什么都不动。已配对的对端可以直接发来 `v = 1000000` 的登记（或 `v = 999999` 的墓碑，本机随后恢复），它按规则被采纳并随同步传开，此后这个会话在各台设备上都无法再删除。不设防：配对即信任（见「权限」一行），它本来就能删除任何会话；任何有限的上限都有这一格，按「离本机登记太远就不认」来挡，分几步照样能顶到，还会让各设备对同一条登记的取舍不一致 |
| 磁盘上的会话目录与附件文件 | 不删（与此前一致）。保留副本的附件恢复后还要用；清理规则待定，判据应是「会话行已不存在（含隐藏行）」，不能用附件同步的引用表 |
| 权限 | 任何已配对设备都能删除或恢复任何会话——与「已配对的设备等同本机」一致，传播删除不新增权限 |

## 6. 审计与广播

审计事件（载荷不含标题与消息内容）：`session.deleted`、`session.deleted.remote`（含 `by`、`via`、`retained`、`unseenCount`、`annotationCount`）、
`session.retained.released`、`session.restored`、`session.restored.remote`、`session.retained.purged`、
`session.stale-copy.rejected`（每个（会话，对端）在进程生命周期内只记一次）。本机从没有过的会话的墓碑不记审计。

广播 `chat.sessions.lifecycle`（`SessionLifecycleNotice`）：`deleted` / `tombstone-applied` / `retained-released` / `restored` / `restore-applied` / `purged`。
`deleted` 与 `tombstone-applied` 广播时该会话已从 `chat.sessions.list` 消失、它的 run 已收尾。合并新建了会话行或让保留副本重新可见时广播 `chat.sessions.changed`。

## 7. 与 OpenMinis 的对接约定（只定契约，未验证）

不声明 `tombstones` 的 OM 构建按旧版对待（§5 第一行）。要声明这个能力位，OM 一侧需要：存每个会话的登记并按 §1 的全序取最大值；
按 §3.2、§3.3 判定；seen 用消息 id 集合算（摘要算法见 §1）；带偶数登记的每个载荷都带 `session`；来自这条传输的墓碑不设过期。
与 PortableRecord `deletes` 项的对应：`id = "SessionV2:<sessionId>"`，其余字段进 `fields`。

## 8. 双机验收清单（留给 F12）

每一步的证据：两端 `sync.list` 的墓碑头清单逐行相等、`audit.list` 里的 `session.*` 事件、界面截图。

1. 两台设备配对，同步两轮，会话与消息一致。
2. A 删除一个会话时 B 离线；B 重连后该会话在 B 上消失、不回到 A。反方向再做一遍。
3. B 离线时在一个会话里追加消息，A 同时删除它；B 重连后该会话进入 B 的「已在其他设备删除」，条数正确；在 B 上恢复，会话回到 A 且含追加的消息。
4. A 暂停同步后删除一个会话，B 上仍在；A 恢复同步后 B 上删除。
5. 把其中一台的系统时间调快或调慢数天，重复第 2、3 步，结果不变。
6. 第三台设备带着旧副本只与其中一台配对：不复活，它自己的副本被清除或保留。
