## 1. 帧

除 `terminal.output` 外，引擎经 `RpcServer.broadcast` 发出的每一条通知在帧顶层多一个成员：

```json
{ "jsonrpc": "2.0", "method": "chat.event", "params": { … }, "ev": { "epoch": 7, "seq": 1234 } }
```

- `method` / `params` 与以前逐字相同；只读这两项的客户端（CLI、对端引擎的 `OutboundClient`）不受影响。
- `seq` 在一个代次内从 1 起逐条加一、无空洞；分配顺序 = 每条连接上的发送顺序。没有任何连接时照常分配并留进窗口。
- 序列化失败不占号。`pairing` 连接收不到广播，也调不了 `state.*`。加密通道上 `ev` 随整帧加密。
- 保留窗口只在内存里：缺省最近 8192 条 / 8 000 000 字符（先到者为准），引擎重启即空。被挤出窗口的帧当场释放（不等内部数组整理），留存的帧字符数不超过这个上限（单帧超上限时窗口里只剩它）。实测一个「260 段正文 + 一次 4000 字写文件」的回合是 267 条事件、80 595 字符（每帧约 300 字符），窗口约合三十个这样的回合。

### 新广播怎么入序（给后续任务）

**照常调 `rpc.broadcast(method, params)` 就自动入序、自动进保留窗口、可被续传。** 不需要也不允许别处自己拼通知帧（`tests/state-sync-wiring.test.ts` 的 W2 钉着：`src/minisd` 里拼通知帧的只有 `rpc/server.ts` 与 `rpc/event-log.ts`）。

两条约束：

1. **先提交、后发布，中间不得有等待 I/O 的 `await`。** `state.attach` 是一段同步代码，它看到的库、账本、broker、尾巴必须与 `seq ≤ lastSeq` 的事件一致。状态改了、事件隔一个 I/O 才发，快照就会带上「事件还没发生」的状态，客户端随后又把那条事件应用一遍。
2. **`coveredBySnapshot` 是一张白名单**（`src/shared/event-stream.ts`）。客户端取快照时，缓冲里水位之前的帧分两类：快照已经带着其效果的（白名单内）丢弃；其余照常交给处理器。维护规则：
   - 新广播**不**往 `StateSnapshot` 里放对应状态（多数情况：一条「请重取」的提示，如 `checkpoints.changed`、会话生命周期广播）→ 什么都不用做，它默认不在白名单里，水位之前的那一帧会照常交付，处理器重拉即可。这类处理器必须是幂等的。
   - 新广播的效果**同时**进了 `StateSnapshot`（往快照加了字段）→ 把这个方法加进 `coveredBySnapshot`。不加的话水位之前的那类帧会在装完快照之后再交付一次：处理器是幂等重拉时无害，带增量语义（追加、计数）时会重复应用。
   - 现在白名单里的四类：`permission.request`、`permission.resolved`、`chat.sessions.changed`、带 `event` 字段的 `chat.event`。`kind: 'synced'` 的 `chat.event` 不在里面。

## 2. `state.attach`

`AttachParams { resume?: StreamCursor; sessionId?: string; protocol?: number } → AttachResult`。同步处理器（函数体里没有 `await`，W1 钉着）。

判定（按序）：

| 条件 | 应答 |
|---|---|
| 没带游标，或三个字段形状不对 | 快照 / `no-cursor` |
| `epoch` 或 `instanceId` 与引擎不同 | 快照 / `epoch-changed` |
| `lastSeq` 比引擎的还大 | 快照 / `ahead` |
| 游标已被挤出保留窗口 | 快照 / `window-expired` |
| 回放超过 2 000 000 字符 | 快照 / `replay-too-large` |
| 其余 | 续传：`events` = `(游标, lastSeq]` 的全部帧，连续升序 |

两种应答的公共头：`{ protocol: 1, epoch, instanceId, lastSeq, revision, window: { firstSeq, maxEvents, maxChars } }`。

- **续传**另带 `runs`、`pendingPermissions`（`lastSeq` 时刻的权威值）。
- **快照**另带 `snapshot: StateSnapshot`：`sessions`（与 `chat.sessions.list` 同形）、`runs` 与 `executions`（`RunLedger.snapshot()`：全部活动 run，加所带会话的最近一次 run）、`live`（各活动 run 的流式尾巴）、`pendingPermissions`、`artifacts`（所列 run 里声明了写入目标或产生了卸载文件的调用）；给了 `sessionId` 再带 `session { sessionId, exists, messages }`。

**已删除的会话不进应答**（与 F11B 的口径相同：不显示、拒写）。「已删除」= 生命周期登记是删除态（`ChatStore.isDeleted`），含两种：已清除的，与「对端删了、本机因为有对方没见过的内容而留着」的保留副本。`chat.prompt` 的入口闸、`chat.runs.snapshot` 的过滤、`checkpoints.*` 读的是同一个判据。

- `sessions` 与 `session.exists` 本来就不含它们（`listSessions` / `getSession` 不返回隐藏的会话行）；带着已删除会话的 `sessionId` 来时 `session` 是 `{ exists: false, messages: [] }`，客户端落到欢迎页。
- 保留副本的账本行还在库里（显式恢复之后要用），所以 `runs`、`executions`、`artifacts`、`live` 按会话另滤一遍；续传应答的 `runs` 同样。会话显式恢复之后它们照常回来。
- 删除落地时，事件保留窗口中该会话的内容帧（含权限预览、检查点与注释通知）替换为 `method: 'state.redacted', params: {}`，只保留原 `ev`。序号不留洞；生命周期与会话列表通知仍可回放。显式恢复会话只恢复持久历史，不恢复已清空的旧事件帧。续传处理器也检查删除登记，清空生命周期钩子之后晚到的会话载荷；客户端按原序号前进，空帧没有状态效果。
- `pendingPermissions` 不另滤：会话被删除时它挂着的卡已经了结（本机删除与对端墓碑都先停 run、了结卡片，再落库），而登记答复资格与返回值必须是同一批卡。
- 往快照里加按会话归属的字段时，照这个办法滤（`tests/state-sync-lifecycle.test.ts` 的 X1–X3、`tests/state-attach.test.ts`）。

**无缝边界**：`lastSeq` 与各项状态在同一段同步代码里取，其间不可能插进任何一次广播、账本事务或权限卡的登记 / 了结；所以快照已含 `seq ≤ lastSeq` 的全部事件的效果（在快照覆盖的域上），之后的增量从 `lastSeq + 1` 起一条不缺。应答里的对象都是这次调用新建的，序列化之前不会被后来的事件改写。

**`revision`**：持久状态修订号 = SQLite 的 `total_changes()`（本连接的行变更总数，每个代次从 0 起，单调不减）。同一代次下 `(lastSeq, revision)` 相同 ⇒ 两份快照除 `takenAt` / `remainingMs` 外内容相同。没有对应事件的库写入（建会话、改绑定、`beginRun`、心跳、审计）也会让它变大，保证是单向的。

**流式尾巴**（`RunLiveView { runId, sessionId, generation, epoch, text, thinking, truncated?, seq }`）：最近一个重置点之后已发布的正文与思考。重置点 = `messagePersisted`、`retry`、`fallback`；`turnEnd` / `error` 删除条目。每个缓冲上限 1 000 000 字符，超过标 `truncated`。客户端显示「历史（所带会话的 `messages`）+ 尾巴」。

副作用只有一类：把调用连接登记为全部待批卡的可答复连接（见 §4），第一次登记写一条 `permission.redelivered` 审计（不广播）。

## 3. 客户端规则（`StreamTracker`）

1. 每条入序帧按游标判定：别的代次 → `foreign`（丢弃，取快照）；`seq ≤ lastSeq` → 重复（丢弃）；`seq === lastSeq + 1` → 应用；其余 → 空洞（扣住这一帧，带游标 attach）。乱序不另设重排：提前到的表现为空洞，晚到的表现为重复。
2. **发 `state.attach` 之前就开始扣帧**：处理器同步返回后要过一个微任务才发应答，比水位更新的帧可能先于应答到达。
3. 应答到了：快照 → 先把缓冲里水位之前的 **run 终止事件**（`turnEnd` / `error`，见下）交给处理器、装快照、把缓冲里水位之前且快照没覆盖的帧（每个 `seq` 一条）交给处理器、再交付水位之后接得上的帧；续传 → 逐条交付回放、用应答里的 `runs` / `pendingPermissions` 校正、再交付缓冲里接得上的帧。续传应答对不上（回放里有洞、走完对不上水位）→ 整份不采用，改取快照。
   - **为什么终止事件要先交付**（`StreamTracker.settle` 的 `ended`）：run 的结局快照里有，所以它算「已覆盖」、不会在装完快照之后再交付一遍；但终止事件自带的东西快照里没有——错误的分类码与接力草稿（`relayDraft`）、截断说明（`outputLimit`）。这条连接明明收到了这一帧，当成已覆盖丢掉的话，上层只能凭账本里的一行 run 去交代，重试 / 接力入口与截断说明就没了。典型时序：别处起的回合第一条事件到达，当前会话的窗口发出 join 的 attach，紧跟着的 `error` 落在水位之前。只在原来有同一代次的游标时给；新连接（缓冲清过）、换了代次、首次同步恒为空，那几种情形由快照里那次 run 的终态收口。
   - 后续任务若让某类已覆盖的帧带上快照里没有的一次性内容，照这个办法处理，不要指望快照补得回来。
4. `missed`：取快照时原来有同一代次的游标，而 `(原游标, 水位]` 的帧没有在缓冲里凑齐——其中快照没覆盖的那些无从补发，上层要整体刷新。
5. 重连用新套接字：旧套接字上扣下的帧不带过去；旧套接字晚到的帧、应答、关闭一律不认（按套接字序号）。

`StreamTracker` 没有 I/O，别的客户端（CLI、已配对设备的界面）可以直接复用。

## 4. 权限卡：补发与答复资格

一张待批的卡接受两类连接的答复：

- 发卡时已经连着的（F13 的原规则）；
- 引擎经 `state.attach` 把这张卡的**完整内容**交给过的（两种应答都带 `pendingPermissions`）。

所以重载、重连后的新连接**必须先 `state.attach`、拿到卡片当前内容，才获得答复资格**；凭旧 `requestId` 直接答复仍是 `applied: false, undelivered: true`，卡不动。旧连接（套接字已关）发不出帧；旧代次的 `requestId` 在新引擎里不认识（`applied: false`）。卡了结时登记随条目一起消失；补发不延长时限。

`PendingPermissionView { requestId, req, meta, origin, askedAt, remainingMs }`：`requestId` / `req` / `meta` 与当初 `permission.request` 广播的 `params` 相同；`remainingMs` 是应答那一刻离超时还剩多少（客户端据它算倒计时，不依赖两边时钟一致）。

## 5. 写调用：不重发，先查询（`state.outcomes`）

**客户端从不因为重连而发出任何写调用。** 断线时已发出、没等到应答的调用，新连接上一帧都不会再出现；结果未知的先查询，未被接收时由用户决定是否重试。

`{ refs: WriteRef[] }`（最多 64 条）→ `{ epoch, instanceId, outcomes: WriteOutcome[] }`，只读。

| `WriteRef` | `WriteOutcome` |
|---|---|
| `{ kind: 'prompt', sessionId, promptId }` | `accepted`（带当前的 `RunView`，状态如实，含 `interrupted`）；`not-accepted`（没送达，或起跑前失败——带 `error`；同一个 `promptId` 可以再提交）。命中的 run 还在 `starting` 时等它的起跑结果再答 |
| `{ kind: 'permission', requestId }` | `pending`；`settled` + `source: 'broker'`（本进程了结的卡，带 `PermissionSettledInfo`）；`settled` + `source: 'ledger'`（执行账本里的审批记录，可以是前一代的：`approval { state, reason?, cause? }` 与 `execution`）；`unknown` |

真实取值：有序关停时挂着的卡 → `ledger` / `denied` / `reason: 'cancelled'` / `cause: 'shutdown'`；进程被杀时挂着的卡 → `ledger` / `expired` / `cause: 'engine-restarted'`、`execution: 'cancelled'`；经桥发起的卡不在账本里 → `unknown`。不认识的 `kind` 报错「不支持的查询类型」。

**已删除的会话**（已清除的与保留副本，判据同 §2）：`prompt` 一律答 `not-accepted`、`error` 是「会话已删除」——与 `chat.prompt` 入口闸对同一个 `promptId` 的答法相同，不等起跑结果、不带出保留副本的 run（它的账本行还在，不拦的话会答 `accepted`）。`permission` 走账本那一支命中已删除会话的执行记录时答 `unknown`；本进程的 broker 记得的卡照答（那是这张卡怎么了结的，会话被删时就是「已取消」，不含执行记录）。客户端的会话列表里已经没有这个会话，这些结论只用来摘掉在途记录，不留说明。

手动重试沿用原 `promptId`：引擎按它持久去重（F05），万一原来那一帧其实晚到了也不会起第二个 run。

## 6. 渲染端的重连

- 由 store 调 `rpc.enableRecovery(hooks)` 开启；不开启时 `RpcClient` 与以前相同（断线即终态）。引擎回「未知方法: state.attach」（旧引擎）时自动关闭。
- 断线：在途调用全部以原文案拒绝（带「在途」标记）、不保存请求帧；`connection = 'reconnecting'`，运行条、权限卡、已流出的正文都留着，发送 / 批准 / 停止 / 换会话不执行。
- 退避：0.5、1、2、4、8、8、8、8 秒（±20%），8 次不成进入终态（横幅带「重新连接」与「重启应用」）。**每次尝试都重新向主进程取端口与 token**（`minisd:info`）；主进程说 `alive: false`（引擎进程已退出）则立即进入终态。
- 连上后带游标 `state.attach`。**闸在应答被采用之后、向上层交付任何东西之前打开**：回放帧的处理器要发调用（重取历史、重拉列表），闸晚开一步这些调用全被拒。
- 同步完成后：不分续传还是快照，一律整体刷新没有广播的域（provider、模型组、权限档位……）并重取当前会话（带会话的快照）；然后核对在途的发送与权限答复（§5）。
  - 整体刷新（`refreshAll`）也带上靠「请重取」类广播维护、而快照不含的域：F11B 的保留副本列表（`chat.sessions.listRetained`）；并把 `refreshTick` 加一，自己取数、不往 store 放状态的组件（F08「改动」页的清单与审阅面板）watch 它重取。这类广播（`chat.sessions.lifecycle`、`checkpoints.changed`）丢在断线里、重连又走快照时不会补发。新增这类域的任务：store 里的加进 `refreshAll`，组件自己取数的 watch `refreshTick`。
- **会话消失**有四条路：本窗口删除、`chat.sessions.lifecycle`（别的窗口或别的设备删的）、`chat.sessions.changed`、快照（断线期间被删）。都经 `markGone`：运行标记、待批卡、别处起跑的记录、跟踪的 run、寄存的说明、核对出「没有送达」的那一条、断线时在途等核对的发送与权限答复，凡属于这个会话的一并放下；谁先到结果相同。核对的查询挂着时会话消失了，结论到达后只摘条目，也不给它寄存说明（同一个 id 日后被带回来时不带着删除之前的旧话）。正开着的会话被删：
  - 收到生命周期广播（在线时；或断线期间被删、重连走**续传**，这条广播在回放里）→ 切到别的会话（别的设备删的多说一句「刚才打开的会话已在另一台设备上删除」），没有别的会话就落到欢迎页。`onSessionLifecycle` 重拉会话列表之后立刻切走，保留副本列表同时发起、不排在切走之前：重连后 `afterSync` 紧跟着带旧会话取一份快照，切走要是再等一个往返，那份快照（`exists: false`）先到，视图就落到欢迎页、那一句也不说了（`tests/renderer-state-e2e.test.ts` E12、`tests/renderer-state-recovery.test.ts` 整合组）。
  - 只有快照（断线期间被删、广播已不在保留窗口里，或引擎重启过）→ 落到欢迎页；这条路不知道是谁删的，不说那一句，也不替用户挑下一个会话。
  - 两条路都清重载记忆。
- 核对结果按会话交代，不只对当前会话：
  - 发送**没有送达**：记在 `undelivered` 里。是当前会话就当场留一条带「重试」的说明；用户当时在看别的会话的话，切回那个会话时（`open()`）把乐观气泡接回末尾、说明补上——重试沿用原 `promptId`。重试（或在这个会话改发别的一条）被引擎当场拒绝时——会话正在运行、模型还没配好、附件已不在、关停中——这条记录、气泡与带「重试」的说明原样放回：重试不经输入卡，没有草稿可交还。只有一次发送真的被接收（或结果未知、转入核对）才放下它。槽位只有一个：等待期间别的会话核对出了新的一条时不覆盖；会话已删的不放回——删除运行中的会话时引擎先停 run，重试的「已取消」应答先于删除的应答（或别的窗口删除时的广播）到达，那一刻放回去的那一条在会话随后消失时由 `markGone` 清掉。
  - 发送**已接收且已结束**：那次 run 的终止事件可能已经在回放里处理过（收口不说第二遍），核对之后兜底摘一次运行标记，那个会话不会一直标着在跑。断线期间以失败结束而重连走的是快照时，由核对结果交代那一条错误条。
  - 权限答复的结局、进入终态时「是否送达未知」：是当前会话进事件条，不是就按会话寄存，切过去时放出来（只说一次；「请重新选择」只在那张卡仍待批时说）。寄存只在内存里，重载即无。
- 收口（run 的终止事件没有到过这条连接、只能凭快照里的终态交代）时的错误条与 `error` 事件同一口径：账本里 failed 的 `stopReason` 就是那条事件的 code——上下文已满 / 思考块绑定 / 能力不符 / 请求放不下不给重试，其余在这次 run 落过 user 消息时给重试；短句按 code。接力草稿与截断说明随事件走、账本里没有，这条路补不回「新建会话接力」与截断说明。
- 断线期间写进 `lastError` 的三句（已断开 / 正在重新连接，连上后再发送 / 连接恢复后才能停止）在连上的那一刻清掉。
- 静默探测：有活动 run 或待批卡而 20 秒没有任何帧时带游标 attach 一次（挡尾帧丢失、半开连接）；有别处正在起跑（`starting`，连 MCP 期间不发事件）的 run 时每 2 秒一次。
- 晚到事件：每个会话记着本窗口跟踪的那次 run（`runId` / `generation` / 是否已结束）。已结束的 run 的事件、更早的 run 的事件、别的代次的事件、已从列表里消失的会话的事件，整条丢弃。会话从列表里消失时这条记录一并作废：引擎删会话时连 run 行一起删，同一个 id 被对端同步带回来之后 `generation` 从 1 重来，旧记录留着会把新 run 的事件全部挡掉。

主进程不在引擎崩溃后重启引擎：产品里引擎崩溃后仍需重启应用（协议已支持只换引擎：重连时游标的代次对不上，取新快照）。

## 7. 给 F07 的契约（运行中插话与排队消息）

扩展点都留成了「可选字段 / 联合类型末尾追加」，旧客户端忽略不认识的部分：

| 要做的事 | 怎么接 |
|---|---|
| 送达回执、排队消息的查询 | 在 `WriteRef` / `WriteOutcome` 的联合**末尾**追加一种 `kind`（如 `{ kind: 'input', … }`），`createOutcomesHandler` 加一个分支；引擎与客户端一起加（引擎对不认识的 `kind` 报错） |
| 快照里带排队消息 | 往 `StateSnapshot` 加**可选**字段，填充点在 `createAttachHandler` 的那段同步代码里（水位自动一致）；`isAttachResult` 只校验必备字段，不用改 |
| 排队 / 插话的新广播 | 照常 `rpc.broadcast`；若它的效果同时进了快照，把方法加进 `coveredBySnapshot`（§1） |
| `chat.cancel` 带 `runId` | 本任务没有动 `chat.cancel`；渲染端 `runOf[sessionId]` 记着本窗口跟踪的 `runId` / `generation`，可直接取用。本任务从不自动重发 cancel |
| 新的写 RPC | 带请求 id，断线时按「不重发 + `isInFlightLoss` + `state.outcomes` 核对」处理；渲染端 `lib/conn/in-doubt.ts` 的只读白名单之外的方法一律按写处理 |
| 插话作废权限卡 | 仍走 broker 的 `settleWhere`，与 `deliver()` 无关 |

约束：提交与对应事件的发布之间不得出现等待 I/O 的 `await`（§1）；`chat.event` 的三个发布点（F05 的守卫）与 `emitRunEvent` 不要绕过 `rpc.broadcast`。
